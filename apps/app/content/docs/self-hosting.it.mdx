QRdx è distribuito con licenza AGPL-3.0 e puoi eseguire l'app web (editor di QR code, account, verifica in due passaggi e passkey, codici dinamici e pagine ospitate, team, temi salvati, galleria della community e questa documentazione) sul tuo server. Il single sign-on del workspace e il registro di controllo del workspace fanno eccezione: si trovano nelle cartelle `ee/` con licenza commerciale e restano disattivati finché non imposti una chiave di licenza (`QRDX_EE_LICENSE`). Per usarli in produzione serve un accordo scritto con QRdx; consulta [LICENSING.md](https://github.com/bucharitesh/qrdx/blob/main/LICENSING.md). Non ti serve nulla di tutto questo per usare la [libreria React `qrdx`](/docs/getting-started) o la CLI. Funzionano ovunque senza backend, con licenza MIT. [Open source in QRdx](/open-source-qr-code-generator) elenca ogni parte del repository e la relativa licenza.

<Callout type="warn">
  La configurazione Docker è nuova. Se qualcosa non funziona, [apri una issue](https://github.com/bucharitesh/qrdx/issues).
</Callout>

## Requisiti [#requirements]

- Docker con Compose v2 e BuildKit (Docker Desktop e le versioni attuali di Docker Engine includono entrambi), oppure Node.js 22 (22.22.3 o successivo) e [Bun](https://bun.com/docs/installation) 1.4 per la configurazione manuale
- Almeno 8 GB di memoria per Docker durante la build dell'immagine
- Un modo per accedere, così da poter creare gli account: un'app OAuth di GitHub o Google, oppure [Resend](https://resend.com) per i codici di accesso via email. I codici vengono inviati per email solo quando `NEXT_PUBLIC_APP_URL` non è `localhost`. `bun run dev` li stampa invece nel terminale, ma l'immagine Docker no, quindi per un test locale con Docker serve l'accesso con GitHub o Google.
- Postgres: il container incluso in `docker-compose.yml`, oppure un database [Neon](https://neon.tech)

### Come funziona la connessione al database [#how-the-database-connection-works]

L'app comunica con Postgres tramite il driver HTTP serverless di Neon.

- **Neon:** funziona direttamente. Imposta `DATABASE_URL` con la tua stringa di connessione Neon.
- **Postgres standard:** richiede davanti un proxy HTTP compatibile con Neon. `docker-compose.yml` ne avvia uno ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) e imposta `DATABASE_HTTP_ENDPOINT` in modo che l'app invii lì le sue query.

Lo schema proviene da `packages/database/schema.ts` e viene applicato con `drizzle-kit push`.

## Avvio rapido con Docker Compose [#quick-start-with-docker-compose]

### 1. Clona il repository [#1-clone-the-repository]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
```

### 2. Configura l'ambiente [#2-configure-the-environment]

```bash
cp apps/app/.env.example .env
```

Modifica `.env`:

- `BETTER_AUTH_SECRET`: generane uno con `openssl rand -base64 32`
- `NEXT_PUBLIC_APP_URL`: l'URL pubblico della tua istanza, ad esempio `https://qr.example.com`. Per un test locale lascia `http://localhost:3000`.
- `BETTER_AUTH_URL`: decommentalo e usa lo stesso valore
- `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`: da una [app OAuth di GitHub](https://github.com/settings/developers) con l'URL di callback `<your url>/api/auth/callback/github`
- oppure `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`: da un [client OAuth di Google](https://console.cloud.google.com/apis/credentials) con l'URI di reindirizzamento `<your url>/api/auth/callback/google`

Non devi impostare `DATABASE_URL`. Compose collega l'app al suo container Postgres. Per cambiare la password del database, imposta `POSTGRES_PASSWORD` prima del primo avvio.

### 3. Avvia lo stack [#3-start-the-stack]

```bash
docker compose up -d --build
```

Questo comando compila l'immagine, avvia Postgres e il proxy, esegue il servizio una tantum `migrate` (`drizzle-kit push`) e poi avvia l'app sulla porta 3000. La prima build richiede diversi minuti.

```bash
docker compose ps                    # migrate should show "exited (0)"
docker compose logs -f migrate app   # follow the schema sync and the app
```

### 4. Crea il tuo primo utente [#4-create-your-first-user]

Apri `NEXT_PUBLIC_APP_URL` in un browser e accedi con GitHub, Google o un codice via email. L'account viene creato al primo accesso.

### 5. Crea il tuo primo admin [#5-create-your-first-admin]

Aggiungi a `.env` l'indirizzo email dell'account che hai appena creato:

```bash
ADMIN_EMAILS=you@example.com
```

Ricrea il container dell'app in modo che rilevi la modifica, poi accedi e apri `/admin`:

```bash
docker compose up -d app
```

`ADMIN_USER_IDS` funziona allo stesso modo, ma con gli id utente.

## Usare Neon o un altro database gestito [#using-neon-or-another-managed-database]

Puoi saltare il Postgres incluso ed eseguire solo l'immagine dell'app:

```bash
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Imposta `DATABASE_URL` in `.env` con la tua stringa di connessione Neon e lascia `DATABASE_HTTP_ENDPOINT` non impostato. Applica lo schema una volta (e di nuovo dopo ogni aggiornamento) con l'immagine del migrator:

```bash
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Configurazione manuale (Node.js) [#manual-setup-nodejs]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
bun install

cp apps/app/.env.example apps/app/.env.local            # then edit it

bun run db:push                                          # apply the schema
bun run --filter app dev                                 # http://localhost:3000
```

Per la produzione, compila e avvia l'app:

```bash
bun x turbo build --filter=app
bun run --filter app start
```

`bun run db:push` si connette con il driver di Neon, quindi richiede un database Neon. Per usare invece il Postgres di Docker nello sviluppo locale, avvialo con `docker compose up -d db db-proxy`, applica lo schema con `docker compose run --rm migrate` e imposta questi valori in `apps/app/.env.local`:

```bash
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

## Reverse proxy e HTTPS [#reverse-proxy-and-https]

Metti l'app dietro un reverse proxy come Caddy, nginx o Traefik che termini il TLS, e non esporre direttamente la porta 3000 a internet. La limitazione della frequenza, le email di sicurezza e il [registro di audit](/docs/help/teams/audit-log) leggono l'IP del client da `X-Real-IP` e poi dal primo indirizzo di `X-Forwarded-For`, quindi il proxy deve impostare questi header e l'app deve essere raggiungibile solo tramite il proxy. Fai in modo che il proxy imposti `X-Real-IP` sull'indirizzo da cui ha ricevuto la connessione (in nginx, `proxy_set_header X-Real-IP $remote_addr;`). Un proxy che si limita ad aggiungere valori a `X-Forwarded-For` permette a un client di mettere qualsiasi indirizzo per primo.

Una volta configurato HTTPS, cambia `NEXT_PUBLIC_APP_URL` e `BETTER_AUTH_URL` con l'URL `https://`, aggiorna gli URL di callback OAuth e ricompila.

### Content-Security-Policy [#content-security-policy]

Le build di produzione inviano una Content-Security-Policy sulle pagine di QRdx: le pagine con accesso effettuato ricevono un nonce di script nuovo a ogni richiesta, le pagine predisposte in anticipo una allowlist di host di script. Le pagine ospitate (`/p`) ricevono una policy permissiva, perché eseguono i pixel del proprietario e incorporano contenuti multimediali da qualsiasi origine. Se il tuo reverse proxy imposta a sua volta `Content-Security-Policy`, i browser applicano entrambe, quindi omettila lì. Imposta `CSP_REPORT_ONLY=1` (in fase di build e in fase di esecuzione) per inviare la policy in modalità solo report mentre verifichi una nuova configurazione; le violazioni vengono registrate da `/api/csp-report`. Aggiungi `CSP_HTTPS=1` quando servi su HTTPS fuori da Vercel, così i browser aggiornano a HTTPS ogni risorsa `http://`.

## Aggiornamento [#updating]

Prima fai un backup del database:

```bash
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Poi scarica gli aggiornamenti e ricompila. Il servizio `migrate` sincronizza di nuovo lo schema prima dell'avvio dell'app.

```bash
git pull
docker compose up -d --build
```

Per l'installazione manuale, esegui `git pull`, `bun install` e `bun run db:push`, poi ricompila.

Se una modifica allo schema eliminasse dei dati, `drizzle-kit push` chiede conferma. In quel caso, esegui `docker compose run --rm migrate` in un terminale per esaminare e confermare le modifiche.
## Risoluzione dei problemi [#troubleshooting]

- **"Invalid environment variables" all'avvio:** il log indica il nome di ogni variabile mancante o non valida. Le variabili opzionali devono essere commentate, non impostate con un valore vuoto.
- **"BETTER_AUTH_SECRET is missing" o "You are using the default secret":** imposta `BETTER_AUTH_SECRET` e ricrea il container.
- **`redirect_uri` OAuth non corrispondente:** l'URL di callback nella tua app OAuth deve essere esattamente `<NEXT_PUBLIC_APP_URL>/api/auth/callback/<github|google>`. Imposta `BETTER_AUTH_URL` sullo stesso URL di base.
- **L'app non riesce a raggiungere il database (`fetch failed`):** con Postgres standard, `DATABASE_HTTP_ENDPOINT` deve puntare al proxy in esecuzione. Controlla `docker compose ps db-proxy`.
- **`migrate` non termina mai:** `drizzle-kit push` è in attesa di una conferma. Vedi [Aggiornamento](#updating).
- **Un valore `NEXT_PUBLIC_*` modificato non ha effetto:** ricostruisci l'immagine.
- **La porta 4444 è già in uso:** cambia la mappatura della porta di `db-proxy` in `docker-compose.yml`. La usa solo lo sviluppo locale sull'host.
- **"the --mount option requires BuildKit":** il tuo Docker non ha BuildKit. Installa il plugin `buildx` oppure aggiorna Docker.
- **La build si interrompe con `Killed` o con codice di uscita 137:** Docker ha esaurito la memoria. Assegnagli almeno 8 GB (Docker Desktop: Settings → Resources) ed esegui di nuovo `docker compose up -d --build`.
- **"sign-in code email is off for this deployment":** le email con il codice non vengono inviate finché `NEXT_PUBLIC_APP_URL` è `localhost`. Per un test in locale usa l'accesso con GitHub o Google.
