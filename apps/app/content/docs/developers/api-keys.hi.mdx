API key की मदद से आपके अपने सर्वर, स्क्रिप्ट और CI जॉब बिना OAuth फ़्लो के [REST API](/docs/developers/rest-api) कॉल कर सकते हैं। इसे `Authorization` हेडर में भेजें:

```bash
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

जो भी endpoint OAuth access token लेता है, वह उसी हेडर में key भी लेता है, और [image API](/docs/developers/image-api) को दोनों में से कुछ नहीं चाहिए। जब आपका प्रोडक्ट दूसरे QRdx यूज़र्स की ओर से काम करता है, तो इसके बजाय [OAuth app](/docs/developers/build-an-integration) इस्तेमाल करें, ताकि हर व्यक्ति उसे मंज़ूरी दे।

## key बनाएँ [#create-a-key]

1. जिस वर्कस्पेस के लिए key चाहिए, उसमें [Settings → API keys & apps](/dashboard?to=settings/developers&new=1) खोलें। यह लिंक आपका आखिरी इस्तेमाल किया हुआ वर्कस्पेस खोलता है; दूसरा वर्कस्पेस चुनने के लिए वर्कस्पेस स्विचर इस्तेमाल करें।
2. **Create key** चुनें। key का नाम उस जगह के नाम पर रखें जहाँ वह चलेगी, उसका access चुनें और चाहें तो एक्सपायरी की तारीख भी चुनें। key आपके बिना भी काम करती है, इसलिए QRdx पहले आपसे [पुष्टि करने को कहता है कि यह आप ही हैं](/docs/help/privacy-and-security/two-step-verification#confirm-its-you), जब तक कि आपने उसी ब्राउज़र में पिछले 10 मिनट में यह न किया हो।
3. key कॉपी करें। यह सिर्फ़ एक बार दिखती है: QRdx उसका सिर्फ़ हैश स्टोर करता है, इसलिए उसे दोबारा नहीं दिखाया जा सकता। उसी डायलॉग में एक curl रिक्वेस्ट भी दिखती है, जिसमें key और इस साइट का API पता भरा होता है, पेस्ट करने के लिए तैयार।

key `qrdx_` से शुरू होती है और उसके बाद 40 अक्षर और अंक होते हैं। लिस्ट में सिर्फ़ उसकी शुरुआत दिखती है, जैसे `qrdx_7KpQ2m…`, ताकि आप keys को अलग पहचान सकें।

## Access [#access]

keys वही स्कोप इस्तेमाल करती हैं जो OAuth apps करते हैं। key बनाते समय तीन विकल्पों में से एक चुनें:

| Access | स्कोप | क्या करने देता है |
| --- | --- | --- |
| Full access | `profile:read`, `themes:read`, `codes:read`, `codes:write` | API जो कुछ भी करता है |
| Read only | `profile:read`, `themes:read`, `codes:read` | कोड, स्कैन एनालिटिक्स, थीम और प्रोफ़ाइल पढ़ना |
| Custom | जो आप चुनें | जो वे स्कोप अनुमति देते हैं ([स्कोप की लिस्ट](/docs/developers/rest-api#get-an-access-token)) |

`codes:write` वह सब भी करने देता है जो `codes:read` करने देता है। key के स्कोप बाद में बदले नहीं जा सकते; इसके बजाय नई key बनाएँ। key के स्कोप से बाहर की रिक्वेस्ट पर `403 INSUFFICIENT_SCOPE` मिलता है, और मैसेज में उस स्कोप का नाम होता है जो चाहिए था।

## वर्कस्पेस और रोल [#workspaces-and-roles]

key उस वर्कस्पेस की होती है जो उसे बनाते समय खुला था, और वहाँ आपके तौर पर काम करती है:

- key उस वर्कस्पेस के कोड, स्कैन, hooks और थीम के साथ काम करती है, वर्कस्पेस के प्लान और [रोज़ का कोटा](/docs/developers/rest-api#rate-limits) के तहत।
- वह वही कर सकती है जो आप उस वर्कस्पेस में कर सकते हैं, हर रिक्वेस्ट के समय आपके [रोल](/docs/teams) के हिसाब से। अपने वर्कस्पेस में आप ओनर होते हैं। अगर आपका रोल बदलता है, तो key के अधिकार भी उसके साथ बदलते हैं; अगर आप वर्कस्पेस छोड़ देते हैं, तो key काम करना बंद कर देती है, और वर्कस्पेस डिलीट करने पर उसकी keys भी डिलीट हो जाती हैं।

वर्कस्पेस का हर सदस्य keys बना सकता है। ओनर और एडमिन वर्कस्पेस की हर key देखते हैं और किसी को भी रद्द कर सकते हैं; सदस्य सिर्फ़ अपनी keys देखते और रद्द करते हैं। `GET /v1/me` key बनाने वाले व्यक्ति की प्रोफ़ाइल लौटाता है।

## एक्सपायरी, आखिरी इस्तेमाल और रद्द करना [#revoke]

- **एक्सपायरी।** key कभी एक्सपायर नहीं होती, या 30 दिन, 90 दिन या 1 साल बाद एक्सपायर होती है। एक्सपायर हुई key को `401 INVALID_TOKEN` मिलता है और वह लिस्ट में **Expired** के निशान के साथ तब तक रहती है जब तक आप उसे रद्द न करें।
- **आखिरी इस्तेमाल।** लिस्ट में हर key की वह तारीख दिखती है जब उसने आखिरी बार कोई रिक्वेस्ट ऑथेंटिकेट की।
- **रद्द करना।** key के बगल में **Revoke** चुनें। उसके बाद उससे की गई रिक्वेस्ट को `401 INVALID_TOKEN` मिलता है। रद्द करना वापस नहीं किया जा सकता।

हर व्यक्ति के हर वर्कस्पेस में ज़्यादा से ज़्यादा 25 सक्रिय keys हो सकती हैं। रद्द की गई और एक्सपायर हुई keys गिनती में नहीं आतीं।

## keys को सुरक्षित रखें [#keep-keys-safe]

- key को सर्वर पर रखें: environment variable या secret manager में। उसे कभी वेब पेज, मोबाइल app, प्रॉम्प्ट या रिपॉज़िटरी में न डालें।
- हर उस जगह के लिए एक अलग key इस्तेमाल करें जहाँ वह चलती है, ताकि एक को रद्द करने से बाकी न टूटें।
- जो स्क्रिप्ट सिर्फ़ रिपोर्ट करती हैं, उन्हें read-only key दें, और कम समय चलने वाले जॉब को ऐसी key दें जो एक्सपायर हो जाए।
- अगर कोई key लीक हो जाए, तो उसे रद्द करें और नई बनाएँ। `qrdx_` प्रीफ़िक्स की वजह से कोड और लॉग में keys आसानी से खोजी जा सकती हैं।

## सेल्फ़-होस्टिंग [#self-hosting]

[सेल्फ़-होस्टेड](/docs/self-hosting) इंस्टेंस के डेटाबेस में `api_key` टेबल होनी चाहिए, जिसे अपडेट के बाद होने वाला सामान्य स्कीमा सिंक बनाता है (Docker के साथ `migrate` सर्विस, नहीं तो `bun run db:push`; देखें [अपडेट करना](/docs/self-hosting))। जब तक वह टेबल नहीं बनती, Settings → API keys & apps बताता है कि API keys उपलब्ध नहीं हैं और API keys को `401` के साथ मना कर देता है। उसका API अपने ही डोमेन पर `/api/v1` पर होता है, और नई key वाला डायलॉग यही पता भरता है।
