O QRdx tem licença AGPL-3.0 e você pode rodar o app web (editor de QR code, contas, verificação em duas etapas e passkeys, códigos dinâmicos e páginas hospedadas, equipes, temas salvos, galeria da comunidade e esta documentação) no seu próprio servidor. O login único (SSO) do workspace e o log de auditoria do workspace são a exceção: eles ficam nas pastas `ee/`, com licença comercial, e continuam desativados a menos que você defina uma chave de licença (`QRDX_EE_LICENSE`). Usá-los em produção exige um acordo por escrito com o QRdx; veja [LICENSING.md](https://github.com/bucharitesh/qrdx/blob/main/LICENSING.md). Você não precisa de nada disso para usar a [biblioteca React `qrdx`](/docs/getting-started) ou a CLI. Elas rodam em qualquer lugar, sem backend.

<Callout type="warn">
  A configuração com Docker é nova. Se algo não funcionar, [abra uma issue](https://github.com/bucharitesh/qrdx/issues).
</Callout>

## Requisitos [#requirements]

- Docker com Compose v2 e BuildKit (o Docker Desktop e o Docker Engine atual já incluem os dois), ou Node.js 22 (22.22.3 ou posterior) e [Bun](https://bun.com/docs/installation) 1.4 para a configuração manual
- Pelo menos 8 GB de memória para o Docker durante o build da imagem
- Uma forma de entrar, para que seja possível criar contas: um app OAuth do GitHub ou do Google, ou o [Resend](https://resend.com) para códigos de login por e-mail. Os códigos só são enviados por e-mail quando `NEXT_PUBLIC_APP_URL` não é `localhost`. O `bun run dev` mostra os códigos no terminal, mas a imagem Docker não, então um teste local com Docker exige login com GitHub ou Google.
- Postgres: o contêiner incluído no `docker-compose.yml` ou um banco do [Neon](https://neon.tech)

### Como funciona a conexão com o banco de dados [#how-the-database-connection-works]

O app se comunica com o Postgres pelo driver HTTP serverless do Neon.

- **Neon:** funciona direto. Defina `DATABASE_URL` com a sua string de conexão do Neon.
- **Postgres comum:** precisa de um proxy HTTP compatível com o Neon na frente. O `docker-compose.yml` roda um ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) e define `DATABASE_HTTP_ENDPOINT` para que o app envie suas consultas para lá.

O schema vem de `packages/database/schema.ts` e é aplicado com `drizzle-kit push`.

## Início rápido com Docker Compose [#quick-start-with-docker-compose]

### 1. Clone o repositório [#1-clone-the-repository]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
```

### 2. Configure o ambiente [#2-configure-the-environment]

```bash
cp apps/docs/.env.example .env
```

Edite o `.env`:

- `BETTER_AUTH_SECRET`: gere um com `openssl rand -base64 32`
- `NEXT_PUBLIC_APP_URL`: a URL pública da sua instância, por exemplo `https://qr.example.com`. Mantenha `http://localhost:3000` para um teste local.
- `BETTER_AUTH_URL`: descomente e use o mesmo valor
- `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`: de um [app OAuth do GitHub](https://github.com/settings/developers) com a URL de callback `<your url>/api/auth/callback/github`
- ou `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`: de um [cliente OAuth do Google](https://console.cloud.google.com/apis/credentials) com a URI de redirecionamento `<your url>/api/auth/callback/google`

Você não precisa definir `DATABASE_URL`. O Compose aponta o app para o contêiner de Postgres dele. Para mudar a senha do banco, defina `POSTGRES_PASSWORD` antes da primeira inicialização.

### 3. Inicie a stack [#3-start-the-stack]

```bash
docker compose up -d --build
```

Isso faz o build da imagem, inicia o Postgres e o proxy, executa o serviço pontual `migrate` (`drizzle-kit push`) e depois inicia o app na porta 3000. O primeiro build leva vários minutos.

```bash
docker compose ps                    # migrate should show "exited (0)"
docker compose logs -f migrate app   # follow the schema sync and the app
```

### 4. Crie seu primeiro usuário [#4-create-your-first-user]

Abra `NEXT_PUBLIC_APP_URL` em um navegador e entre com GitHub, Google ou um código por e-mail. Sua conta é criada no primeiro login.

### 5. Crie seu primeiro admin [#5-create-your-first-admin]

Adicione ao `.env` o endereço de e-mail da conta que você acabou de criar:

```bash
ADMIN_EMAILS=you@example.com
```

Recrie o contêiner do app para que ele aplique a mudança, depois entre e abra `/admin`:

```bash
docker compose up -d app
```

`ADMIN_USER_IDS` funciona da mesma forma, com IDs de usuário.

## Usando o Neon ou outro banco de dados gerenciado [#using-neon-or-another-managed-database]

Você pode dispensar o Postgres incluído e rodar apenas a imagem do app:

```bash
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Defina `DATABASE_URL` no `.env` com a sua string de conexão do Neon e deixe `DATABASE_HTTP_ENDPOINT` sem definir. Aplique o schema uma vez (e de novo após cada atualização) com a imagem do migrator:

```bash
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Configuração manual (Node.js) [#manual-setup-nodejs]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
bun install

cp apps/docs/.env.example apps/docs/.env.local          # then edit it

bun run db:push                                          # apply the schema
bun run --filter docs dev                                # http://localhost:3000
```

Para produção, faça o build e inicie o app:

```bash
bun x turbo build --filter=docs
bun run --filter docs start
```

O `bun run db:push` se conecta usando o driver do Neon, então precisa de um banco do Neon. Para usar o Postgres do Docker no desenvolvimento local, inicie-o com `docker compose up -d db db-proxy`, aplique o schema com `docker compose run --rm migrate` e defina o seguinte em `apps/docs/.env.local`:

```bash
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

## Variáveis de ambiente [#environment-variables]

O [`apps/docs/.env.example`](https://github.com/bucharitesh/qrdx/blob/main/apps/docs/.env.example) lista todas as variáveis, com uma nota curta sobre onde obter cada uma.

### Mínimo [#minimum]

| Variável | Finalidade |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | URL pública da sua instância |
| `DATABASE_URL` | String de conexão do Postgres (definida pelo Compose) |
| `BETTER_AUTH_SECRET` | Assina sessões e cookies |

Adicione um provedor OAuth (GitHub ou Google), ou o Resend para códigos de login por e-mail, para que as pessoas consigam entrar.

## Proxy reverso e HTTPS [#reverse-proxy-and-https]

Coloque o app atrás de um proxy reverso, como Caddy, nginx ou Traefik, que encerre o TLS, e não exponha a porta 3000 diretamente à internet. O limite de taxa, os e-mails de segurança e o [log de auditoria](/docs/help/teams/audit-log) leem o IP do cliente de `X-Real-IP` e, depois, do primeiro endereço de `X-Forwarded-For`; por isso o proxy precisa definir esses cabeçalhos e o app só deve ser acessível por ele. Faça o proxy definir `X-Real-IP` com o endereço de onde recebeu a conexão (no nginx, `proxy_set_header X-Real-IP $remote_addr;`). Um proxy que apenas acrescenta valores a `X-Forwarded-For` permite que o cliente coloque qualquer endereço na primeira posição.

Depois de configurar o HTTPS, altere `NEXT_PUBLIC_APP_URL` e `BETTER_AUTH_URL` para a URL `https://`, atualize as URLs de callback do OAuth e refaça o build.

### Content-Security-Policy [#content-security-policy]

Os builds de produção enviam uma Content-Security-Policy nas páginas do próprio QRdx: as páginas com login recebem um nonce de script novo a cada requisição, e as páginas pré-renderizadas recebem uma lista de hosts de script permitidos. As páginas hospedadas (`/p`) recebem uma política mais permissiva, porque executam os pixels do dono e incorporam mídia de qualquer lugar. Se o seu proxy reverso também define `Content-Security-Policy`, os navegadores aplicam as duas, então deixe de fora no proxy. Defina `CSP_REPORT_ONLY=1` (em tempo de build e em tempo de execução) para enviar a política apenas em modo de relatório enquanto você verifica uma nova configuração; as violações são registradas em `/api/csp-report`. Adicione `CSP_HTTPS=1` quando você servir por HTTPS fora da Vercel, para que os navegadores promovam qualquer recurso `http://`.

## Atualização [#updating]

Primeiro, faça backup do banco de dados:

```bash
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Depois, baixe as mudanças e refaça o build. O serviço `migrate` sincroniza o schema novamente antes de o app iniciar.

```bash
git pull
docker compose up -d --build
```

Na configuração manual, execute `git pull`, `bun install` e `bun run db:push`, e depois refaça o build.

Se uma mudança no schema apagar dados, o `drizzle-kit push` pede confirmação. Nesse caso, execute `docker compose run --rm migrate` em um terminal para revisar e confirmar as mudanças.
## Solução de problemas [#troubleshooting]

- **"Invalid environment variables" na inicialização:** o log mostra o nome de cada variável ausente ou inválida. Variáveis opcionais devem ficar comentadas, não definidas com um valor vazio.
- **"BETTER_AUTH_SECRET is missing" ou "You are using the default secret":** defina `BETTER_AUTH_SECRET` e recrie o contêiner.
- **Erro de `redirect_uri` incompatível no OAuth:** a URL de callback no seu app OAuth deve ser exatamente `<NEXT_PUBLIC_APP_URL>/api/auth/callback/<github|google>`. Defina `BETTER_AUTH_URL` com a mesma URL base.
- **O app não consegue acessar o banco de dados (`fetch failed`):** com Postgres puro, `DATABASE_HTTP_ENDPOINT` deve apontar para o proxy em execução. Verifique com `docker compose ps db-proxy`.
- **`migrate` nunca termina:** o `drizzle-kit push` está esperando uma confirmação. Veja [Atualização](#updating).
- **Um valor alterado de `NEXT_PUBLIC_*` não tem efeito:** reconstrua a imagem.
- **A porta 4444 já está em uso:** altere o mapeamento de porta do `db-proxy` em `docker-compose.yml`. Só o desenvolvimento local no host usa essa porta.
- **"the --mount option requires BuildKit":** seu Docker não tem BuildKit. Instale o plugin `buildx` ou atualize o Docker.
- **A build para com `Killed` ou com código de saída 137:** o Docker ficou sem memória. Dê a ele pelo menos 8 GB (Docker Desktop: Settings → Resources) e execute `docker compose up -d --build` de novo.
- **"sign-in code email is off for this deployment":** os e-mails com código não são enviados enquanto `NEXT_PUBLIC_APP_URL` for `localhost`. Use o login com GitHub ou Google para um teste local.
