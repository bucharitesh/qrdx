REST APIのエラーは、どのエンドポイントから返される場合でも、同じ形式のJSONです。

```json
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

| フィールド | 内容 |
| --- | --- |
| `code` | 下の表にある、安定した機械可読のコードです。処理の分岐にはこの値を使ってください。 |
| `message` | 何が問題で、どう修正すればよいかを人向けに説明した文です。文言は変更される場合があります。 |
| `status` | HTTPステータスです（重複して含まれます）。 |
| `docs` | 修正方法を説明するページです。該当するページがある場合のみ含まれます。 |
| `data` | 一部のエラーに付く追加情報です。`VALIDATION_ERROR` では、各問題が `data.details` に一覧で入ります。 |

バリデーションエラーでは、失敗したすべてのフィールドが示されます。

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid request body",
  "status": 400,
  "data": {
    "details": [
      { "path": "destinationUrl", "message": "Enter a full URL, starting with https://" }
    ]
  }
}
```

Image APIでは、クエリパラメータは `{ "path", "message" }` ではなく `{ "param", "message" }` の形式で報告されます。

## エラーコード [#error-codes]

| ステータス | コード | 意味 | 対処方法 |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | ボディ、クエリ、またはパスがバリデーションに失敗しました。`data.details` に各問題が `{ path, message }` の形式で一覧表示されます（Image APIでは `{ param, message }`）。ボディがコードの配列の場合は、その行の `index` も付きます。 | `data.details` に挙げられたフィールドを修正して、リクエストを再送してください。 |
| 400 | `INVALID_SLUG` | カスタムバックハーフ（`slug`）がルールに違反しています。予約語である場合や、1回のリクエスト内で同じバックハーフが重複している場合です。配列の場合、`data.details` に各行が `index` 付きで一覧表示されます。 | 別のバックハーフを選んでください。メッセージに違反したルールが示されます。 |
| 400 | `TOO_MANY_CODES` | 1回のリクエストに含まれるコードが1,000件を超えています。通常は、ボディのスキーマが先にこれを `VALIDATION_ERROR` として拒否します。 | 1回のリクエストで送るコードは最大1,000件にしてください。 |
| 400 | `DOMAIN_NOT_VERIFIED` | `domainId` が、まだ検証されていないカスタムドメインを指しています。 | ドメインページでドメインの検証を完了するか、`domainId` を省略してください。 |
| 400 | `SID_REQUIRED` | コンバージョンに、スキャンの `qrdx_sid`（ブラウザから送る場合）、または `sid` もしくは `code`（サーバーから送る場合）が含まれていません。 | ショートリンクがページURLに追加した `qrdx_sid` を送ってください。APIキーまたはトークンを使う場合は、コードIDを `code` として送ってください。 |
| 401 | `UNAUTHORIZED` | 認証情報がありません。リクエストに `Authorization: Bearer` ヘッダーがありません（QRdxのブラウザセッションもありません）。 | APIキーを `Authorization: Bearer <key>` として送ってください。キーは設定 → APIキーとアプリで作成できます。OAuthアクセストークンも同じヘッダーで送ります。 |
| 401 | `INVALID_TOKEN` | APIキーまたはアクセストークンが不明、失効済み、または期限切れです（アクセストークンの有効期間は1時間です）。または、キーの作成者がBANされたか、そのキーのワークスペースを退出しました。 | キー全体を送信したか確認するか、新しいキーを作成してください。アクセストークンの場合は、リフレッシュトークンで新しいトークンを取得するか、ユーザーに再度認可を行ってもらってください。 |
| 402 | `PLAN_REQUIRED` | ワークスペースのプランでは利用できない機能です。一括作成、カスタムバックハーフ、カスタムドメインにはProが、コンバージョンとフックにはBusinessが必要です。 | ワークスペースをアップグレードするか、その機能をリクエストから外してください。 |
| 402 | `LIMIT_REACHED` | ワークスペースの有効な動的QRコードの数が、プランに含まれる上限に達しています（フリーは10件）。 | コードをアーカイブするか（アーカイブ済みのコードは数に含まれません）、Proにアップグレードして無制限にしてください。 |
| 403 | `INSUFFICIENT_SCOPE` | APIキーまたはトークンは有効ですが、このエンドポイントに必要なスコープがありません。 | メッセージに示されたスコープを持つキーを作成してください（キーのスコープは変更できません）。OAuthアプリの場合は、スコープを追加し、ユーザーの認可時にそのスコープを要求してください。 |
| 403 | `FORBIDDEN` | 呼び出し元にはこの操作の権限がありません。たとえば、ワークスペースのメンバーが他の人が作成したコードを削除する場合、メンバーがフックを管理する場合、別のサイトからブラウザセッションで書き込みを行う場合です。APIキーでは、そのワークスペースにおける作成者のロールで許可されている操作だけが行えます。 | ワークスペースのオーナーまたは管理者に依頼するか、サーバーからAPIキーを使ってAPIを呼び出してください。 |
| 403 | `CONFIRMATION_REQUIRED` | サインイン済みのブラウザセッションでフックを作成するには、直近の「本人確認」が必要です。APIキーとOAuthトークンでは求められません。 | QRdxで本人確認を行い、10分以内にもう一度試すか、サーバーからAPIキーを使ってフックを作成してください。 |
| 403 | `CONVERSIONS_OFF` | コンバージョントラッキングが有効になっていないコードに対して、ブラウザからコンバージョンが送られました。 | そのコードのコンバージョントラッキングを有効にするか、サーバーからAPIキーを使ってコンバージョンを報告してください。 |
| 403 | `LIMIT_REACHED` | ワークスペースにすでにWebhookエンドポイントとフックが合計20件あります。 | 使わなくなったエンドポイントまたはフックを削除してください。 |
| 404 | `NOT_FOUND` | そのようなエンドポイントがないか、コード、フック、テーマ、カスタムドメインが、キーまたはトークンが操作するワークスペースに存在しません。 | パスとIDを確認してください。APIキーは作成されたワークスペースを対象に動作し、OAuthトークンはそのユーザー自身のワークスペースを対象に動作します。 |
| 404 | `INVALID_SID` | `qrdx_sid` が不明であるか、帰属期間である30日より古いものです。 | 最近のスキャンの `qrdx_sid` を送るか、サーバーからコードIDを指定してコンバージョンを報告してください。 |
| 409 | `SLUG_TAKEN` | そのドメインで、すでに別のコードがそのバックハーフを使っています。配列の場合、使用済みのものが `data.details` に `index` 付きで一覧表示され、何も作成されません。 | 別のバックハーフを選んでください。 |
| 413 | `PAYLOAD_TOO_LARGE` | ボディがエンドポイントの上限を超えています。コードは4 MB、フックは16 KB、コンバージョンは8 KBです。また、レスポンス（各コードとそのデザイン）が4 MBを超えるコードのバッチも対象で、この場合は何も作成されません。 | ボディを小さくしてください。コードの場合は、大きなインラインロゴが原因であることが多く、バッチの場合は `Prefer: return=minimal` を送るか、コードの数を減らしてください。 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | `Content-Type: application/json` なしで書き込みが行われました。 | `Content-Type: application/json` を付けて、JSONのボディを送ってください。 |
| 422 | `UNSAFE_DESTINATION` | Google Web Riskが宛先URLを危険と判定しました（マルウェア、フィッシング、または不要なソフトウェア）。配列の場合、判定された各行が `data.details` に `index` 付きで一覧表示され、何も作成されません。 | 別の宛先を使ってください。判定が誤りである場合は、Googleにサイトの再審査を依頼してください。 |
| 429 | `RATE_LIMITED` | リクエストが多すぎます。1分あたりの制限（設定されるのは `Retry-After` のみ）か、ワークスペースの1日のクォータ（`Retry-After` と `X-RateLimit-*`）に達しています。 | `Retry-After` の秒数だけ待ってください。1日のクォータの場合は、00:00 UTCまで待つか、プランをアップグレードしてください。 |
| 500 | `INTERNAL_ERROR` | QRdx側で何かが失敗しました。内容はログに記録されています。 | しばらくしてからもう一度試してください。繰り返し発生する場合は、リクエストの時刻を添えて報告してください。 |
| 503 | `SLUG_UNAVAILABLE` | 時間内に、空いているショートリンクのスラッグを確保できませんでした。 | 同じリクエストをもう一度送ってください。 |
| 503 | `UNAVAILABLE` | このデプロイメントではカスタムドメインが設定されていません（カスタムドメインのないセルフホストのインスタンスです）。 | `domainId` を省略するか、インスタンスでカスタムドメインを設定してください。 |

## リトライ [#retrying]

- **`429`：** `Retry-After` に示された秒数だけ待ってから、同じリクエストを送ってください。1日のクォータを使い切った場合は、`X-RateLimit-*` ヘッダーに、プランで許可されているリクエスト数と、カウントがリセットされる時刻（00:00 UTC）が示されます。[レート制限](/docs/developers/rest-api#rate-limits)を参照してください。
- **`500` と `503`：** 約1秒から始めて、指数バックオフでリトライしてください。
- **その他の `4xx`：** 同じリクエストは同じ理由で失敗します。まず原因を修正してください。

コードの作成は冪等ではありません。`POST /v1/codes` がタイムアウトした場合は、再送する前にコードの一覧を確認してください。そうしないと、コードが2つ作成される可能性があります。コンバージョンは冪等です。独自の `id` を送ると、再送時には `200` と `duplicate: true` が返ります。

## `/v1/me` と `/v1/themes` [#v1me-and-v1themes]

この2つのエンドポイントは、同じボディに加えて、従来から返しているOAuthのフィールド `error` と `error_description`（`message` と同じ文）も返します。これにより、古いクライアントも引き続き動作します。

| `error` | `code` |
| --- | --- |
| `invalid_token` | UNAUTHORIZED または INVALID_TOKEN |
| `insufficient_scope` | INSUFFICIENT_SCOPE |
| `rate_limited` | RATE_LIMITED（1日のクォータ） |
| `not_found` | NOT_FOUND（themes） |

## OAuthエンドポイント [#oauth-endpoints]

`https://qrdx.dev/api/oauth` 配下のOAuthエンドポイント（authorize、token、revoke、userinfo）は、代わりにOAuth 2.0の標準に従い、`{ "error", "error_description" }` を返します。`error` は `invalid_request`、`invalid_client`、`invalid_grant`、`unsupported_grant_type`、`invalid_token`、`access_denied` のいずれかです。リフレッシュ時に `invalid_grant` が返された場合は、リフレッシュトークンがすでに使用済み（リフレッシュのたびに新しいトークンが返されます）、30日で期限切れ、またはユーザーがアプリを取り消したことを意味します。その場合は、ユーザーに再度認可を行ってもらってください。[REST APIとOAuth](/docs/developers/rest-api#get-an-access-token)を参照してください。

## 存在しないエンドポイント [#unknown-endpoints]

`/v1` 配下に存在しないパスへリクエストすると、HTML ページではなく、JSON 形式の `404 NOT_FOUND` が返されます。すべてのエンドポイントは [APIリファレンス](/docs/developers/api) で確認できます。
