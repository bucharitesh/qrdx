APIキーを使うと、OAuthのフローなしで、ご自身のサーバー、スクリプト、CIジョブから[REST API](/docs/developers/rest-api)を呼び出せます。キーは `Authorization` ヘッダーで送信します。

```bash
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

OAuthアクセストークンを受け付けるエンドポイントは、同じヘッダーでキーも受け付けます。[Image API](/docs/developers/image-api)はどちらも不要です。お使いのプロダクトが他のQRdxユーザーに代わって操作する場合は、代わりに[OAuthアプリ](/docs/developers/build-an-integration)を使ってください。そうすれば、各ユーザーが個別に承認します。

## キーを作成する [#create-a-key]

1. キーを使うワークスペースで[設定 → APIキーとアプリ](/dashboard?to=settings/developers&new=1)を開きます。このリンクは最後に使ったワークスペースを開きます。別のワークスペースを使う場合は、ワークスペース切り替えで選択してください。
2. **キーを作成**を選びます。キーを実行する場所に合わせて名前を付け、アクセス権を選び、必要であれば有効期限も設定します。キーはあなたがいなくても動作するため、QRdxはまず[本人確認](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)を求めます。ただし、そのブラウザーで直近10分以内に確認済みの場合は求められません。
3. キーをコピーします。キーが表示されるのは一度だけです。QRdxにはキーのハッシュしか保存されないため、再表示はできません。同じダイアログには、キーとこのサイトのAPIアドレスが入力済みのcurlリクエストが表示されるので、そのまま貼り付けて使えます。

キーは `qrdx_` に続く40文字の英数字です。一覧には、キーを見分けられるように先頭部分のみ(例:`qrdx_7KpQ2m…`)が表示されます。

## アクセス権 [#access]

キーには、OAuthアプリと同じスコープを使います。キーの作成時に、次の3つから選びます。

| アクセス権 | スコープ | できること |
| --- | --- | --- |
| フルアクセス | `profile:read`、`themes:read`、`codes:read`、`codes:write` | APIで可能なすべての操作 |
| 読み取り専用 | `profile:read`、`themes:read`、`codes:read` | QRコード、スキャン分析、テーマ、プロフィールの読み取り |
| カスタム | 選択したスキャープ | 選択したスコープで許可される操作([スコープ一覧](/docs/developers/rest-api#get-an-access-token)) |

`codes:write` は `codes:read` でできることもすべて許可します。キーのスコープは後から変更できません。変更したい場合は新しいキーを作成してください。キーのスコープ外のリクエストは `403 INSUFFICIENT_SCOPE` となり、メッセージには必要だったスコープ名が示されます。

## ワークスペースとロール [#workspaces-and-roles]

キーは、作成時に開いていたワークスペースに属し、そのワークスペース内であなたとして動作します。

- キーは、そのワークスペースのQRコード、スキャン、フック、テーマに対して使え、ワークスペースのプランと[1日あたりのクォータ](/docs/developers/rest-api#rate-limits)が適用されます。
- キーは、あなたがそのワークスペースで実行できる操作を、リクエストごとにあなたの[ロール](/docs/teams)に基づいて判定したうえで実行できます。ご自身のワークスペースでは、あなたはオーナーです。ロールが変わるとキーの権限も変わります。ワークスペースを退出するとキーは使えなくなり、ワークスペースを削除するとそのキーも削除されます。

ワークスペースのメンバーは全員キーを作成できます。オーナーと管理者はワークスペース内のすべてのキーを確認し、いずれも無効化できます。メンバーは自分のキーのみ確認および無効化できます。`GET /v1/me` は、キーを作成した本人のプロフィールを返します。

## 有効期限、最終使用、無効化 [#revoke]

- **有効期限。** キーは無期限にするか、30日、90日、1年で期限切れになるように設定できます。期限切れのキーは `401 INVALID_TOKEN` になり、無効化するまで**期限切れ**と表示されたまま一覧に残ります。
- **最終使用。** 一覧には、各キーが最後にリクエストの認証に使われた日付が表示されます。
- **無効化。** キーの横にある**無効化**を選びます。それ以降、そのキーでのリクエストは `401 INVALID_TOKEN` になります。無効化は取り消せません。

1人あたり、ワークスペースごとに最大25個の有効なキーを持てます。無効化済みや期限切れのキーは数に含まれません。

## キーを安全に管理する [#keep-keys-safe]

- キーはサーバー上の環境変数またはシークレットマネージャーに保管してください。Webページ、モバイルアプリ、プロンプト、リポジトリには絶対に入れないでください。
- キーは実行場所ごとに1つ使います。そうすれば、他に影響を与えずに1つだけ無効化できます。
- レポートのみ行うスクリプトには読み取り専用キーを、短期間のジョブには期限付きのキーを使ってください。
- キーが漏えいした場合は、無効化して新しいキーを作成してください。`qrdx_` というプレフィックスがあるため、コードやログでキーを検索しやすくなっています。

## セルフホスティング [#self-hosting]

[セルフホスト](/docs/self-hosting)のインスタンスでは、データベースに `api_key` テーブルが必要です。このテーブルは、更新後に通常行うスキーマ同期で作成されます(Dockerでは `migrate` サービス、それ以外では `bun run db:push`。[更新](/docs/self-hosting)を参照してください)。テーブルがない間は、設定 → APIキーとアプリにAPIキーを利用できない旨が表示され、APIはキーを `401` で拒否します。APIはそのインスタンス自身のドメインの `/api/v1` にあり、これが新規キーのダイアログに入力されるアドレスです。
