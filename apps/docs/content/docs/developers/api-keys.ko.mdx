API 키를 사용하면 OAuth 흐름 없이 직접 운영하는 서버, 스크립트, CI 작업에서 [REST API](/docs/developers/rest-api)를 호출할 수 있어요. 키는 `Authorization` 헤더에 담아 보냅니다.

```bash
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

OAuth 액세스 토큰을 받는 모든 엔드포인트는 같은 헤더로 키도 받습니다. [Image API](/docs/developers/image-api)는 둘 다 필요하지 않습니다. 제품이 다른 QRdx 사용자를 대신해 동작해야 한다면 [OAuth 앱](/docs/developers/build-an-integration)을 사용하세요. 그러면 사용자가 각자 승인합니다.

## 키 만들기 [#create-a-key]

1. 키를 사용할 워크스페이스에서 [설정 → API 키 및 앱](/dashboard?to=settings/developers&new=1)을 여세요. 이 링크는 마지막으로 사용한 워크스페이스를 엽니다. 다른 워크스페이스를 쓰려면 워크스페이스 전환기에서 선택하세요.
2. **키 만들기**를 선택하세요. 키가 실행될 위치에 맞게 이름을 정하고, 접근 권한을 고르고, 원하면 만료 시점도 정합니다. 키는 사용자 없이도 동작하므로, 해당 브라우저에서 최근 10분 안에 확인하지 않았다면 QRdx가 먼저 [본인 확인](/docs/help/privacy-and-security/two-step-verification#confirm-its-you)을 요청해요.
3. 키를 복사하세요. 키는 한 번만 표시됩니다. QRdx는 키의 해시만 저장하므로 다시 보여 줄 수 없어요. 같은 대화 상자에는 키와 이 사이트의 API 주소가 채워진 curl 요청이 있어서 바로 붙여넣어 쓸 수 있습니다.

키는 `qrdx_` 뒤에 영문자와 숫자 40자가 붙은 형태입니다. 목록에는 키를 구분할 수 있도록 `qrdx_7KpQ2m…`처럼 앞부분만 표시돼요.

## 접근 권한 [#access]

키는 OAuth 앱과 같은 스코프를 사용합니다. 키를 만들 때 세 가지 중 하나를 고르세요.

| 접근 권한 | 스코프 | 허용 범위 |
| --- | --- | --- |
| 전체 접근 | `profile:read`, `themes:read`, `codes:read`, `codes:write` | API가 하는 모든 작업 |
| 읽기 전용 | `profile:read`, `themes:read`, `codes:read` | QR 코드, 스캔 분석, 테마, 프로필 읽기 |
| 사용자 지정 | 직접 선택한 스코프 | 해당 스코프가 허용하는 작업 ([스코프 목록](/docs/developers/rest-api#get-an-access-token)) |

`codes:write`는 `codes:read`가 허용하는 모든 작업도 허용합니다. 키의 스코프는 나중에 변경할 수 없으니 새 키를 만드세요. 키의 스코프를 벗어난 요청은 `403 INSUFFICIENT_SCOPE`를 받으며, 메시지에 필요했던 스코프 이름이 표시됩니다.

## 워크스페이스와 역할 [#workspaces-and-roles]

키는 만들 때 열려 있던 워크스페이스에 속하며, 그곳에서 사용자로서 동작합니다.

- 키는 해당 워크스페이스의 QR 코드, 스캔, 훅, 테마를 다루며, 워크스페이스의 요금제와 [일일 할당량](/docs/developers/rest-api#rate-limits)이 적용됩니다.
- 키는 사용자가 그 워크스페이스에서 할 수 있는 작업을 할 수 있으며, 각 요청 시점의 [역할](/docs/teams)을 기준으로 판단합니다. 자신의 워크스페이스에서는 소유자입니다. 역할이 바뀌면 키의 권한도 함께 바뀌고, 워크스페이스를 떠나면 키가 작동하지 않으며, 워크스페이스를 삭제하면 그 키도 삭제됩니다.

워크스페이스의 모든 멤버가 키를 만들 수 있습니다. 소유자와 관리자는 워크스페이스의 모든 키를 보고 폐기할 수 있으며, 멤버는 자신의 키만 보고 폐기할 수 있어요. `GET /v1/me`는 키를 만든 사람의 프로필을 반환합니다.

## 만료, 마지막 사용, 폐기 [#revoke]

- **만료.** 키는 만료되지 않게 하거나 30일, 90일, 1년 뒤에 만료되게 할 수 있습니다. 만료된 키는 `401 INVALID_TOKEN`을 받고, 폐기할 때까지 **만료됨**으로 표시된 채 목록에 남아요.
- **마지막 사용.** 목록에는 각 키가 마지막으로 요청을 인증한 날짜가 표시됩니다.
- **폐기.** 키 옆의 **폐기**를 선택하세요. 그 이후 해당 키로 보낸 요청은 `401 INVALID_TOKEN`을 받습니다. 폐기는 되돌릴 수 없어요.

각 사용자는 워크스페이스마다 활성 키를 최대 25개까지 가질 수 있습니다. 폐기되었거나 만료된 키는 포함되지 않아요.

## 키를 안전하게 보관하기 [#keep-keys-safe]

- 키는 서버의 환경 변수나 시크릿 관리자에 보관하세요. 웹 페이지, 모바일 앱, 프롬프트, 저장소에는 절대 넣지 마세요.
- 실행되는 곳마다 키를 하나씩 사용하세요. 그러면 다른 곳에 영향 없이 하나만 폐기할 수 있어요.
- 보고만 하는 스크립트에는 읽기 전용 키를, 짧게 실행되는 작업에는 만료되는 키를 사용하세요.
- 키가 유출되면 폐기하고 새 키를 만드세요. `qrdx_` 접두사 덕분에 코드와 로그에서 키를 쉽게 검색할 수 있습니다.

## 셀프 호스팅 [#self-hosting]

[셀프 호스팅](/docs/self-hosting) 인스턴스에는 데이터베이스에 `api_key` 테이블이 필요합니다. 업데이트 후 일반적인 스키마 동기화를 하면 이 테이블이 만들어져요. Docker에서는 `migrate` 서비스를, 그 외에는 `bun run db:push`를 사용합니다. 자세한 내용은 [업데이트](/docs/self-hosting)를 참고하세요. 테이블이 생기기 전에는 설정 → API 키 및 앱에 API 키를 사용할 수 없다고 표시되고, API는 키를 `401`로 거부합니다. API는 해당 인스턴스의 도메인에서 `/api/v1`로 제공되며, 새 키 대화 상자에 채워지는 주소가 바로 이것입니다.
