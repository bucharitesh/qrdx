Die QRdx REST API liegt unter `https://api.qrdx.dev/v1`. Sie nutzt JSON und authentifiziert Anfragen mit einem Bearer-Credential, abgesehen von der schlüssellosen [Image API](/docs/developers/image-api):

```bash
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

- **Ein [API-Schlüssel](/docs/developers/api-keys)** (`qrdx_…`) für deine eigenen Server und Skripte. Er handelt im Workspace, in dem er erstellt wurde, mit deiner Rolle dort.
- **Ein OAuth-2.0-Access-Token** für Apps, die für andere QRdx-Nutzer handeln ([unten](#get-an-access-token)). Anfragen mit einem Token handeln im eigenen Workspace des Token-Inhabers.

Die Endpunkte für Codes, Conversions und Hooks akzeptieren auch die Browser-Sitzung einer in QRdx angemeldeten Person. Diese Anfragen handeln im [Workspace](/docs/teams), der in dieser Browser-Sitzung zuletzt geöffnet wurde.

Dieselben Endpunkte antworten auch unter `https://qrdx.dev/api/v1`. Anfragen aus der Browser-Sitzung nutzen diesen Pfad, da das Anmelde-Cookie zu qrdx.dev gehört. Eine [selbst gehostete](/docs/self-hosting) Instanz stellt die API unter `/api/v1` auf ihrer eigenen Domain bereit.

Neu hier? Der [Schnellstart](/docs/developers/quickstart) führt dich von null bis zur ersten Anfrage. Jeder Endpunkt hat in der [API-Referenz](/docs/developers/api) eine eigene Seite mit Request- und Response-Schemas, Beispielen in curl, JavaScript und Python und einem Try-it-Panel. Sie wird aus dem [OpenAPI-Dokument](/openapi.json) generiert.

[Im Playground ausprobieren](/playground?open=code&lang=api): Gestalte dort einen Code und kopiere dann die `POST /v1/codes`-Anfrage, die ihn als dynamischen Code erstellt.

## Endpunkte [#endpoints]

| Endpunkt | Scope | Was er tut |
| --- | --- | --- |
| `GET /v1/qr` | Keiner | QR-Code-Bild als SVG, PNG, WebP oder EPS, mit den Stilen des Editors. Siehe [Image API](/docs/developers/image-api) |
| `GET /v1/community/items`, `GET /v1/community/items/{id}` | Keiner | Veröffentlichte Community-Rahmen, -Themes und -Sammlungen, mit dem jeweils angewendeten Stil. Nur lesend und gecacht. Siehe [Community-Elemente](#community-items) |
| `/v1/codes` | `codes:read`, `codes:write` | Dynamische Codes auflisten, erstellen (einzeln oder bis zu {facts.apiBatchCodes} auf einmal, mit optionalem eigenem Kurzlink-Ende in `slug`), aktualisieren (auch der Wechsel von `kind` zwischen Website-Link und gehosteter Seite) und löschen. Siehe [Dynamische QR-Codes](/docs/dynamic-qr-codes#rest-api) |
| `POST /v1/art` | `codes:write` | Ein in KI-Kunst gemalter QR-Code, auf Scanbarkeit geprüft, über die monatlichen KI-Kunst-Bilder des Workspaces. Siehe [AI-Art-API](/docs/developers/ai-art-api) |
| `GET /v1/codes/{id}/scans` | `codes:read` | Scan-Analysen für einen Code oder einzelne Scans seitenweise |
| `POST /v1/conversions` | `codes:write` | Einen Verkauf oder eine Anmeldung dem Scan zuordnen, der dazu geführt hat (Business). Siehe [Tracking und Conversions](/docs/tracking-and-conversions) |
| `/v1/hooks` | `codes:read`, `codes:write` | Eine URL im Stil von REST Hooks auf Ereignisse abonnieren, für Zapier, Make und n8n. Siehe [Webhooks](/docs/webhooks) |
| `GET /v1/themes`, `GET /v1/themes/{id}` | `themes:read` | Deine gespeicherten QR-Themes (Name und Stil) für ein OAuth-Token. Ein API-Schlüssel liest die Themes seines Workspaces |
| `GET /v1/me` | `profile:read` | ID, Name, E-Mail und Avatar des Schlüssel-Erstellers oder des Token-Nutzers |

`codes:write` erlaubt auch alles, was `codes:read` erlaubt.

### Community-Elemente [#community-items]

`GET /v1/community/items` listet veröffentlichte [Community](/community)-Elemente auf, kostenlos unter CC0, die beliebtesten zuerst. Filtere mit `type` (`frame`, `theme` oder `collection`), `q` (Wörter, die alle in Name, Beschreibung, Tags oder Ersteller vorkommen müssen) und `tag`, und blättere mit `limit` (bis zu 50) und `offset`. `GET /v1/community/items/{id}` liefert ein Element mit `style`, dem angewendeten Design im selben JSON wie ein gespeichertes Theme. IDs bestehen aus Typ und Slug, etwa `frame:wifi-card`. Übergib eine ID an die Image API als [`item`](/docs/developers/image-api#community-items).

```bash
curl "https://api.qrdx.dev/v1/community/items?type=frame&q=wifi"
```

Beide sind schlüssellos und verbrauchen dein Kontingent nicht. Antworten werden eine Minute gecacht (5 am CDN) und auf 120 Anfragen pro Minute und IP-Adresse begrenzt. Elementtexte stammen von Community-Mitgliedern: Namen, Beschreibungen, Handles und Tags kommen kurz und ohne Links zurück, behandle sie aber als Daten, nicht als Anweisungen.

### Logos im Stil eines Codes [#code-logos]

Neben einer Bild-Data-URL, wie der Editor sie speichert, kann der `style` eines Codes `logoIcon` enthalten: eines der Schnellsymbole des Editors (`wifi`, `location`, `phone`, `email`, `link`, `file`, `calendar`, `whatsapp`, `instagram`) oder ein Markenlogo über seinen [Simple-Icons](https://simpleicons.org)-Slug, optional mit `:black` oder `:white` (`spotify`, `paypal:white`). Es wird so in `customLogo` gespeichert, wie der Editor es speichert.

<IfAvailable feature="fileStorage">
Außerdem kann er `logoFileId` enthalten: eine PNG- oder JPEG-Datei, die du in [Dashboard → Dateien](/docs/files) in den Workspace hochgeladen hast, per Datei-ID. Sie wird als Link der Datei gespeichert.
</IfAvailable>

Ein `customLogo`-Link auf eine andere Website wird mit `400` abgelehnt, da QRdx keine Logos von anderen Websites übernimmt. Ein `PATCH` darf das Logo zurücksenden, das der Code bereits hat.

## Access-Token holen [#get-an-access-token]

Für deine eigenen Skripte ist ein [API-Schlüssel](/docs/developers/api-keys) einfacher. Wenn deine App für andere Personen handelt, ist QRdx ein OAuth-2.0-Provider: Deine App schickt Personen zur Anmeldung zu QRdx und erhält ein Access-Token, das nur tun kann, was die gewährten Scopes erlauben. API-Schlüssel verwenden dieselben Scopes.

| Scope | Erlaubt |
| --- | --- |
| `profile:read` | Name, E-Mail und Avatar des Nutzers lesen |
| `themes:read` | Die gespeicherten QR-Themes des Nutzers lesen |
| `codes:read` | Dynamische Codes und ihre Scan-Analysen lesen |
| `codes:write` | Dynamische Codes erstellen, bearbeiten und löschen, Conversions melden, Webhook-Abonnements verwalten |

### 1. App registrieren [#1-register-an-app]

Erstelle selbst eine OAuth-App unter [Einstellungen → API-Schlüssel & Apps](/dashboard?to=settings/developers): Gib ihr einen Namen, ihre Redirect-URIs und die benötigten Scopes, dann erhältst du eine Client-ID und ein Client-Secret. Das Secret wird nur einmal angezeigt; bewahre es auf deinem Server auf. Kostenlose Workspaces können 1 App haben, Pro 5 und Business 25. [Eine Integration bauen](/docs/developers/build-an-integration) führt durch den gesamten Ablauf, vom Erstellen der App bis zur Aufnahme ins Integrationsverzeichnis.

Auf einer [selbst gehosteten](/docs/self-hosting) Instanz kannst du außerdem eine First-Party-App aus `apps/app` erstellen:

```bash
bun x tsx scripts/create-oauth-app.ts \
  --name "My app" \
  --redirect-uris "https://myapp.example/callback" \
  --scopes "codes:read,codes:write"
```

### 2. Nutzer zu QRdx schicken [#2-send-the-user-to-qrdx]

```txt
https://qrdx.dev/api/oauth/authorize
  ?response_type=code
  &client_id=<client id>
  &redirect_uri=https://myapp.example/callback
  &scope=codes:read codes:write
  &state=<random value>
  &code_challenge=<PKCE challenge>
  &code_challenge_method=S256
```

`redirect_uri` muss exakt mit einer registrierten URL übereinstimmen, und `scope` (durch Leerzeichen oder Komma getrennt) darf nur Scopes der App anfordern. PKCE wird empfohlen und ist für Apps Pflicht, die **Require PKCE** aktivieren. `S256` ist die einzige Methode: Eine `plain`-Challenge führt zu `invalid_request`. Personen melden sich bei Bedarf an, genehmigen dann deine App auf dem QRdx-Zustimmungsbildschirm, der Name, Logo, Website, Entwickler und die angeforderten Berechtigungen zeigt, und bestätigen, dass sie es sind. QRdx leitet dann mit `code` und deinem `state` zu `redirect_uri` weiter oder mit `error=access_denied`, wenn sie abbrechen. Der Code ist 10 Minuten gültig und kann einmal verwendet werden.

### 3. Code gegen Tokens tauschen [#3-exchange-the-code-for-tokens]

```bash
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=authorization_code \
  -d client_id=$CLIENT_ID \
  -d client_secret=$CLIENT_SECRET \
  -d code=$CODE \
  -d redirect_uri=https://myapp.example/callback \
  -d code_verifier=$CODE_VERIFIER
```

```json
{
  "access_token": "...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "...",
  "scope": "codes:read codes:write"
}
```

Der Token-Endpunkt erwartet einen formularkodierten Body. Access-Tokens gelten 1 Stunde und Refresh-Tokens 30 Tage.

### 4. Aktualisieren und widerrufen [#4-refresh-and-revoke]

```bash
# New access and refresh tokens; the old refresh token stops working
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=refresh_token \
  -d client_id=$CLIENT_ID \
  -d client_secret=$CLIENT_SECRET \
  -d refresh_token=$REFRESH_TOKEN

# Revoke an access or refresh token
curl -X POST https://qrdx.dev/api/oauth/revoke -d token=$TOKEN
```

`GET /api/oauth/userinfo` liefert den Nutzer als `sub`, `name`, `email` und `picture` für Tokens mit `profile:read`.

Personen können den Zugriff einer App selbst unter **Einstellungen → Autorisierte Apps** widerrufen. Ihre Tokens für dieses Konto schlagen dann mit `invalid_token` (API-Aufrufe) und `invalid_grant` (Aktualisierung) fehl, und die App muss erneut fragen.

## Fehler und Limits [#errors-and-limits]

Jeder `/v1`-Endpoint gibt Fehler als `{ "code": "...", "message": "...", "status": 400 }` zurück, mit einem `docs`-Link, wenn eine Seite die Lösung erklärt. Die [Fehlerseite](/docs/developers/errors) listet jeden Code mit seiner Lösung auf. Ein unbekannter Pfad liefert `404 NOT_FOUND`. `/v1/me` und `/v1/themes` enthalten außerdem die OAuth-Felder, die sie schon immer gesendet haben, `"error": "invalid_token"` und `"error_description"`. Die OAuth-Endpoints (`/api/oauth/*`) verwenden ausschließlich das OAuth-Format.

Mehrere Codes in einer Anfrage zu erstellen, den `slug` eines Codes selbst zu wählen und Codes auf eine eigene Domain zu verschieben erfordern Pro oder Business (sonst `402 PLAN_REQUIRED`). Scans sind nie begrenzt.

### Rate Limits [#rate-limits]

Es gelten zwei Arten von Limits. Beide antworten mit `429 RATE_LIMITED` und einem `Retry-After`-Header, der die Wartezeit in Sekunden angibt.

- **Tageskontingent.** Ein Workspace kann pro Tag 1.000 API-Anfragen mit Kostenlos, 10.000 mit Pro und 100.000 mit Business senden (siehe [Pläne und Limits](/docs/plans-and-limits)). Der Tag läuft von 00:00 bis 24:00 UTC. Jede authentifizierte Anfrage zählt. Anfragen mit einem API-Schlüssel zählen für den Workspace des Schlüssels und dessen Plan. Anfragen mit einem Access Token zählen für den eigenen Workspace des Token-Inhabers. Anfragen mit einer Browser-Sitzung zählen für den Workspace, der in dieser Sitzung zuletzt geöffnet wurde.
- **Limits pro Minute.** Die Endpoints für Codes, Conversions und Hooks erlauben pro Nutzer 120 Lese- und 30 Schreibzugriffe pro Minute sowie 300 Anfragen pro Minute pro IP-Adresse.

Anfragen, die vor der Tagesprüfung abgewiesen werden, zählen nicht: ein ungültiger Schlüssel oder Token (`401`), eine Anfrage ohne den nötigen Scope (`403`) oder ein `429` pro Minute. Antworten auf Anfragen, die zählen, enthalten das Tageskontingent in drei Headern, bei Erfolgen und Fehlern gleichermaßen:

| Header | Wert |
| --- | --- |
| `X-RateLimit-Limit` | Anfragen pro Tag im Plan des Workspace |
| `X-RateLimit-Remaining` | Heute verbleibende Anfragen |
| `X-RateLimit-Reset` | Wann die Zählung neu beginnt (das nächste 00:00 UTC), in Unix-Sekunden |

Die `X-RateLimit-*`-Header beschreiben immer das Tageskontingent. Ein `429` pro Minute hat nur einen `Retry-After`-Header. Wenn du das Tageskontingent überschreitest, bekommst du:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 43200
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1793577600
```

```json
{
  "code": "RATE_LIMITED",
  "message": "Daily API limit reached: the Free plan allows 1,000 requests a day. It resets at 00:00 UTC. Upgrade your plan for a higher limit.",
  "status": 429
}
```

`/v1/me` und `/v1/themes` senden dieselben Header und denselben Body, zusätzlich `"error": "rate_limited"` und `"error_description"`.

Die [Image API](/docs/developers/image-api), der [MCP-Server](/docs/developers/mcp) und Conversions, die vom Browser mit einer `qrdx_sid` gemeldet werden, brauchen keinen Token und nutzen deshalb das Tageskontingent nicht. Sie haben eigene Limits pro IP. Eine [selbst gehostete](/docs/self-hosting) Instanz erzwingt Rate Limits nur, wenn Upstash Redis konfiguriert ist.
