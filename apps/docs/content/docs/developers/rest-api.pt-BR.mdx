A REST API do QRdx fica em `https://api.qrdx.dev/v1`. Ela usa JSON e, exceto a [Image API](/docs/developers/image-api), que não precisa de chave, autentica as requisições com uma credencial Bearer:

```bash
curl https://api.qrdx.dev/v1/codes -H "Authorization: Bearer $QRDX_API_KEY"
```

- **Uma [chave de API](/docs/developers/api-keys)** (`qrdx_…`) para os seus próprios servidores e scripts. Ela age no workspace em que foi criada, com o seu papel nele.
- **Um token de acesso OAuth 2.0** para apps que agem em nome de outros usuários do QRdx ([veja abaixo](#get-an-access-token)). As requisições feitas com um token agem no workspace do próprio dono do token.

Os endpoints de códigos, conversões e hooks também aceitam a sessão de navegador de quem está conectado ao QRdx; essas requisições agem no [workspace](/docs/teams) aberto por último nessa sessão do navegador.

Os mesmos endpoints também respondem em `https://qrdx.dev/api/v1`. As requisições da sessão do navegador usam esse caminho, já que o cookie de login pertence a qrdx.dev, e uma instância [auto-hospedada](/docs/self-hosting) serve a API em `/api/v1` no próprio domínio.

Chegou agora? O [início rápido](/docs/developers/quickstart) leva você do zero até a primeira requisição. Cada endpoint tem a sua própria página, com esquemas de requisição e resposta, exemplos em curl, JavaScript e Python e um painel Try it, na [referência da API](/docs/developers/api), gerada a partir do [documento OpenAPI](/openapi.json).

[Teste no Playground](/playground?open=code&lang=api): estilize um código lá e depois copie a requisição `POST /v1/codes` que o cria como código dinâmico.

## Endpoints [#endpoints]

| Endpoint | Escopo | O que faz |
| --- | --- | --- |
| `GET /v1/qr` | Nenhum | Imagem do QR code em SVG, PNG, WebP ou EPS, com os estilos do editor. Veja [Image API](/docs/developers/image-api) |
| `GET /v1/community/items`, `GET /v1/community/items/{id}` | Nenhum | Molduras, temas e coleções da comunidade publicados, com o estilo que cada um aplica. Somente leitura e com cache. Veja [Itens da comunidade](#community-items) |
| `/v1/codes` | `codes:read`, `codes:write` | Lista, cria (um ou até {facts.apiBatchCodes} por vez, com um back-half personalizado opcional em `slug`), atualiza (inclusive trocando `kind` entre um link de site e uma página hospedada) e exclui QR codes dinâmicos. Veja [QR codes dinâmicos](/docs/dynamic-qr-codes#rest-api) |
| `POST /v1/art` | `codes:write` | Um QR code pintado em uma arte de IA, com leitura verificada, usando as imagens de arte de IA mensais do workspace. Veja [API de arte de IA](/docs/developers/ai-art-api) |
| `GET /v1/codes/{id}/scans` | `codes:read` | Análises de leitura de um código, ou leituras individuais página por página |
| `POST /v1/conversions` | `codes:write` | Atribui uma venda ou um cadastro à leitura que levou a ele (Business). Veja [Rastreamento e conversões](/docs/tracking-and-conversions) |
| `/v1/hooks` | `codes:read`, `codes:write` | Assina eventos para uma URL, no estilo REST Hooks, para Zapier, Make e n8n. Veja [Webhooks](/docs/webhooks) |
| `GET /v1/themes`, `GET /v1/themes/{id}` | `themes:read` | Seus temas de QR salvos (nome e estilo) para um token OAuth; uma chave de API lê os temas do seu workspace |
| `GET /v1/me` | `profile:read` | O id, o nome, o e-mail e o avatar de quem criou a chave ou do usuário do token |

`codes:write` também permite tudo o que `codes:read` permite.

### Itens da comunidade [#community-items]

`GET /v1/community/items` lista os itens publicados da [comunidade](/community), grátis sob CC0, dos mais populares para os menos. Filtre com `type` (`frame`, `theme` ou `collection`), `q` (palavras que devem aparecer todas no nome, na descrição, nas tags ou no criador) e `tag`, e pagine com `limit` (até 50) e `offset`. `GET /v1/community/items/{id}` retorna um item com `style`, o design que ele aplica, no mesmo JSON de um tema salvo. Os ids são o tipo e o slug, como `frame:wifi-card`; passe um para a Image API como [`item`](/docs/developers/image-api#community-items).

```bash
curl "https://api.qrdx.dev/v1/community/items?type=frame&q=wifi"
```

Os dois não precisam de chave e não consomem a sua cota. As respostas ficam em cache por um minuto (5 na CDN) e são limitadas a 120 requisições por minuto por endereço IP. O texto dos itens é escrito por membros da comunidade: nomes, descrições, handles e tags voltam curtos e sem links, mas trate-os como dados, não como instruções.

### Logos no estilo de um código [#code-logos]

Além de uma data URL de imagem como o editor salva, o `style` de um código aceita `logoIcon`: um dos ícones rápidos do editor (`wifi`, `location`, `phone`, `email`, `link`, `file`, `calendar`, `whatsapp`, `instagram`), ou o logo de uma marca pelo slug do [Simple Icons](https://simpleicons.org), opcionalmente com `:black` ou `:white` (`spotify`, `paypal:white`). Ele é salvo em `customLogo` como o editor salva.

<IfAvailable feature="fileStorage">
Também aceita `logoFileId`: um PNG ou JPEG que você enviou ao workspace em [Painel → Arquivos](/docs/files), pelo id do arquivo. Ele é salvo como o link do arquivo.
</IfAvailable>

Um link em `customLogo` para outro site é recusado com `400`, já que o QRdx não aceita logos de outros sites. Um `PATCH` pode reenviar o logo que o código já tem.

## Obter um token de acesso [#get-an-access-token]

Para os seus próprios scripts, uma [chave de API](/docs/developers/api-keys) é mais simples. Quando o seu app age em nome de outras pessoas, o QRdx é um provedor OAuth 2.0: o seu app envia as pessoas ao QRdx para entrar e recebe de volta um token de acesso que só pode fazer o que os escopos concedidos permitem. As chaves de API usam os mesmos escopos.

| Escopo | Permite |
| --- | --- |
| `profile:read` | Ler o nome, o e-mail e o avatar do usuário |
| `themes:read` | Ler os temas de QR salvos do usuário |
| `codes:read` | Ler QR codes dinâmicos e as análises de leitura deles |
| `codes:write` | Criar, editar e excluir QR codes dinâmicos, registrar conversões e gerenciar assinaturas de webhook |

### 1. Registre um app [#1-register-an-app]

Crie você mesmo um app OAuth em [Configurações → Chaves de API e apps](/dashboard?to=settings/developers): dê um nome a ele, informe as URIs de redirecionamento e os escopos de que ele precisa, e você recebe um client ID e um client secret. O secret aparece uma única vez; guarde-o no seu servidor. Workspaces Grátis podem ter 1 app, Pro 5 e Business 25. [Criar uma integração](/docs/developers/build-an-integration) mostra todo o fluxo, da criação do app até a listagem dele no diretório de integrações.

Em uma instância [auto-hospedada](/docs/self-hosting), você também pode criar um app próprio a partir de `apps/docs`:

```bash
bun x tsx scripts/create-oauth-app.ts \
  --name "My app" \
  --redirect-uris "https://myapp.example/callback" \
  --scopes "codes:read,codes:write"
```

### 2. Envie o usuário ao QRdx [#2-send-the-user-to-qrdx]

```txt
https://qrdx.dev/api/oauth/authorize
  ?response_type=code
  &client_id=<client id>
  &redirect_uri=https://myapp.example/callback
  &scope=codes:read codes:write
  &state=<random value>
  &code_challenge=<PKCE challenge>
  &code_challenge_method=S256
```

`redirect_uri` precisa ser exatamente igual a uma URL registrada, e `scope` (separado por espaço ou vírgula) só pode pedir os escopos do app. Recomendamos PKCE, que é obrigatório para apps que ativam **Require PKCE**. `S256` é o único método: um desafio `plain` recebe `invalid_request`. As pessoas entram, se for preciso, e depois aprovam o seu app na tela de consentimento do QRdx, que mostra o nome, o logo, o site, quem o criou e as permissões pedidas, e confirmam que são elas mesmas. Em seguida, o QRdx redireciona para `redirect_uri` com `code` e o seu `state`, ou com `error=access_denied` se cancelarem. O código vale por 10 minutos e só pode ser usado uma vez.

### 3. Troque o código por tokens [#3-exchange-the-code-for-tokens]

```bash
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=authorization_code \
  -d client_id=$CLIENT_ID \
  -d client_secret=$CLIENT_SECRET \
  -d code=$CODE \
  -d redirect_uri=https://myapp.example/callback \
  -d code_verifier=$CODE_VERIFIER
```

```json
{
  "access_token": "...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "...",
  "scope": "codes:read codes:write"
}
```

O endpoint de token recebe um corpo codificado como formulário. Os tokens de acesso duram 1 hora e os tokens de atualização 30 dias.

### 4. Atualize e revogue [#4-refresh-and-revoke]

```bash
# New access and refresh tokens; the old refresh token stops working
curl -X POST https://qrdx.dev/api/oauth/token \
  -d grant_type=refresh_token \
  -d client_id=$CLIENT_ID \
  -d client_secret=$CLIENT_SECRET \
  -d refresh_token=$REFRESH_TOKEN

# Revoke an access or refresh token
curl -X POST https://qrdx.dev/api/oauth/revoke -d token=$TOKEN
```

`GET /api/oauth/userinfo` retorna o usuário como `sub`, `name`, `email` e `picture` para tokens com `profile:read`.

As pessoas podem revogar o acesso de um app por conta própria em **Configurações → Apps autorizados**. Os tokens dele para aquela conta passam a falhar com `invalid_token` (chamadas de API) e `invalid_grant` (atualização), e o app precisa pedir de novo.

## Erros e limites [#errors-and-limits]

Todo endpoint `/v1` retorna erros no formato `{ "code": "...", "message": "...", "status": 400 }`, com um link `docs` quando existe uma página que explica a correção; a [página de erros](/docs/developers/errors) lista cada código com a sua correção. Um caminho desconhecido recebe `404 NOT_FOUND`. `/v1/me` e `/v1/themes` também incluem os campos OAuth que sempre enviaram, `"error": "invalid_token"` e `"error_description"`, e os endpoints OAuth (`/api/oauth/*`) usam apenas o formato OAuth.

Criar vários códigos em uma única requisição, escolher o `slug` de um código e mover códigos para um domínio personalizado exigem Pro ou Business (caso contrário, `402 PLAN_REQUIRED`). As leituras nunca são limitadas.

### Limites de requisições [#rate-limits]

Existem dois tipos de limite. Ambos respondem `429 RATE_LIMITED` com um header `Retry-After`, que indica o número de segundos de espera.

- **Cota diária.** Um workspace pode fazer 1.000 requisições de API por dia no plano Grátis, 10.000 no Pro e 100.000 no Business (veja [Planos e limites](/docs/plans-and-limits)). O dia vai de 00:00 a 24:00 UTC. Toda requisição autenticada conta. As requisições feitas com uma chave de API contam para o workspace da chave e o plano dele. As requisições feitas com um token de acesso contam para o workspace próprio do dono do token. As requisições feitas com uma sessão do navegador contam para o último workspace aberto nessa sessão.
- **Limites por minuto.** Os endpoints de códigos, conversões e hooks permitem 120 leituras e 30 escritas por minuto por usuário, e 300 requisições por minuto por endereço IP.

Requisições recusadas antes da verificação diária não contam: chave ou token inválido (`401`), requisição sem o escopo necessário (`403`) ou um `429` por minuto. As respostas às requisições que contam trazem a cota diária em três headers, tanto em sucessos quanto em erros:

| Header | Valor |
| --- | --- |
| `X-RateLimit-Limit` | Requisições por dia no plano do workspace |
| `X-RateLimit-Remaining` | Requisições restantes hoje |
| `X-RateLimit-Reset` | Quando a contagem recomeça (o próximo 00:00 UTC), em segundos Unix |

Os headers `X-RateLimit-*` sempre descrevem a cota diária. Um `429` por minuto traz apenas o header `Retry-After`. Ao passar da cota diária, você recebe:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 43200
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1793577600
```

```json
{
  "code": "RATE_LIMITED",
  "message": "Daily API limit reached: the Free plan allows 1,000 requests a day. It resets at 00:00 UTC. Upgrade your plan for a higher limit.",
  "status": 429
}
```

`/v1/me` e `/v1/themes` enviam os mesmos headers e o mesmo corpo, além de `"error": "rate_limited"` e `"error_description"`.

A [Image API](/docs/developers/image-api), o [servidor MCP](/docs/developers/mcp) e as conversões reportadas pelo navegador com um `qrdx_sid` não precisam de token, então não usam a cota diária. Elas têm limites próprios por IP. Uma instância [auto-hospedada](/docs/self-hosting) só aplica limites de requisições quando o Upstash Redis está configurado.
