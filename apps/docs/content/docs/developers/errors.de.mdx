Jeder Fehler der REST API ist JSON mit derselben Struktur, egal welcher Endpunkt ihn zurückgibt:

```json
{
  "code": "INSUFFICIENT_SCOPE",
  "message": "This API key needs the 'codes:write' scope. Create a key that includes it at https://qrdx.dev/dashboard?to=settings/developers; a key's scopes can't be changed.",
  "status": 403,
  "docs": "https://qrdx.dev/docs/developers/api-keys"
}
```

| Feld | Bedeutung |
| --- | --- |
| `code` | Ein stabiler, maschinenlesbarer Code aus der Tabelle unten. Verzweige danach. |
| `message` | Was schiefgelaufen ist und wie du es behebst, für Menschen. Der Wortlaut kann sich ändern. |
| `status` | Der HTTP-Status, wiederholt. |
| `docs` | Eine Seite, die die Lösung erklärt, falls es eine gibt. |
| `data` | Zusätzliche Details bei manchen Fehlern. `VALIDATION_ERROR` listet jedes Problem in `data.details` auf. |

Ein Validierungsfehler nennt jedes Feld, das fehlgeschlagen ist:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid request body",
  "status": 400,
  "data": {
    "details": [
      { "path": "destinationUrl", "message": "Enter a full URL, starting with https://" }
    ]
  }
}
```

Die Image API meldet Query-Parameter als `{ "param", "message" }` statt als `{ "path", "message" }`.

## Fehlercodes [#error-codes]

| Status | Code | Bedeutung | Lösung |
| --- | --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Body, Query oder Pfad haben die Validierung nicht bestanden. `data.details` listet jedes Problem als `{ path, message }` auf (`{ param, message }` bei der Image API), mit dem `index` der Zeile, wenn der Body ein Array von Codes ist. | Korrigiere die Felder in `data.details` und sende die Anfrage erneut. |
| 400 | `INVALID_SLUG` | Der benutzerdefinierte Back-Half (`slug`) verstößt gegen eine Regel: ein reserviertes Wort oder derselbe Back-Half zweimal in einer Anfrage. Bei einem Array listet `data.details` jede Zeile mit `index` auf. | Wähle einen anderen Back-Half. Die Meldung nennt die Regel. |
| 400 | `TOO_MANY_CODES` | Mehr als 1.000 Codes in einer Anfrage. Das Body-Schema lehnt das normalerweise zuerst ab, als `VALIDATION_ERROR`. | Sende höchstens 1.000 Codes pro Anfrage. |
| 400 | `DOMAIN_NOT_VERIFIED` | `domainId` verweist auf eine eigene Domain, die noch nicht verifiziert ist. | Schließe die Verifizierung der Domain auf der Seite „Domains“ ab oder lass `domainId` weg. |
| 400 | `SID_REQUIRED` | Eine Conversion ohne die `qrdx_sid` des Scans (aus dem Browser) oder ohne `sid` oder `code` (von einem Server). | Sende die `qrdx_sid`, die der Short-Link an deine Seiten-URL angehängt hat, oder mit einem API-Schlüssel oder Token die Code-ID als `code`. |
| 401 | `UNAUTHORIZED` | Keine Zugangsdaten: Die Anfrage hat keinen `Authorization: Bearer`-Header (und keine QRdx-Browsersitzung). | Sende einen API-Schlüssel als `Authorization: Bearer <key>`; erstelle einen unter Einstellungen → API-Schlüssel & Apps. OAuth-Zugriffstokens kommen in denselben Header. |
| 401 | `INVALID_TOKEN` | Der API-Schlüssel oder das Zugriffstoken ist unbekannt, widerrufen oder abgelaufen (Zugriffstokens gelten eine Stunde), oder die Person, die den Schlüssel erstellt hat, wurde gesperrt oder hat den Workspace des Schlüssels verlassen. | Prüfe, ob du den ganzen Schlüssel gesendet hast, oder erstelle einen neuen. Hole bei einem Zugriffstoken mit deinem Refresh-Token ein neues oder schicke den Nutzer erneut durch die Autorisierung. |
| 402 | `PLAN_REQUIRED` | Die Funktion ist im Tarif des Workspace nicht enthalten: Massenerstellung, benutzerdefinierte Back-Halves und eigene Domains brauchen Pro; Conversions und Hooks brauchen Business. | Upgrade den Workspace oder lass die Funktion in der Anfrage weg. |
| 402 | `LIMIT_REACHED` | Der Workspace hat so viele aktive dynamische Codes, wie sein Tarif umfasst (10 bei Kostenlos). | Archiviere einen Code (archivierte Codes zählen nicht) oder wechsle zu Pro für unbegrenzte Codes. |
| 403 | `INSUFFICIENT_SCOPE` | Der API-Schlüssel oder das Token ist gültig, hat aber nicht den Scope, den dieser Endpunkt braucht. | Erstelle einen Schlüssel mit dem Scope aus der Meldung (die Scopes eines Schlüssels lassen sich nicht ändern). Füge bei einer OAuth-App den Scope hinzu und fordere ihn an, wenn der Nutzer autorisiert. |
| 403 | `FORBIDDEN` | Der Aufrufer darf das nicht tun: ein Workspace-Mitglied, das einen von jemand anderem erstellten Code löscht, ein Mitglied, das Hooks verwaltet, oder ein Schreibzugriff per Browsersitzung von einer anderen Website. Ein API-Schlüssel kann nur das, was die Rolle seines Erstellers im Workspace erlaubt. | Frag einen Owner oder Admin des Workspace oder rufe die API mit einem API-Schlüssel von deinem Server aus auf. |
| 403 | `CONFIRMATION_REQUIRED` | Zum Erstellen eines Hooks mit einer angemeldeten Browsersitzung ist eine kürzlich erfolgte Bestätigung „Du bist es“ nötig. Bei API-Schlüsseln und OAuth-Tokens wird nicht danach gefragt. | Bestätige in QRdx, dass du es bist, und versuche es dann innerhalb von 10 Minuten erneut, oder erstelle den Hook mit einem API-Schlüssel von deinem Server aus. |
| 403 | `CONVERSIONS_OFF` | Eine Browser-Conversion für einen Code, bei dem das Conversion-Tracking nicht aktiviert ist. | Aktiviere das Conversion-Tracking für den Code oder melde die Conversion mit einem API-Schlüssel von deinem Server aus. |
| 403 | `LIMIT_REACHED` | Der Workspace hat bereits 20 Webhook-Endpunkte und Hooks. | Lösche einen Endpunkt oder Hook, den du nicht mehr brauchst. |
| 404 | `NOT_FOUND` | Es gibt diesen Endpunkt nicht, oder der Code, Hook, das Theme oder die eigene Domain existiert nicht in dem Workspace, in dem der Schlüssel oder das Token handelt. | Prüfe Pfad und ID. Ein API-Schlüssel handelt in dem Workspace, in dem er erstellt wurde; ein OAuth-Token handelt im eigenen Workspace seines Nutzers. |
| 404 | `INVALID_SID` | Die `qrdx_sid` ist unbekannt oder älter als 30 Tage, das Attributionsfenster. | Sende die `qrdx_sid` eines aktuellen Scans oder melde die Conversion per Code-ID von deinem Server aus. |
| 409 | `SLUG_TAKEN` | Ein anderer Code verwendet diesen Back-Half bereits auf dieser Domain. Bei einem Array listet `data.details` jeden vergebenen per `index` auf, und es wird nichts erstellt. | Wähle einen anderen Back-Half. |
| 413 | `PAYLOAD_TOO_LARGE` | Der Body überschreitet das Limit des Endpunkts: 4 MB für Codes, 16 KB für Hooks, 8 KB für Conversions. Gilt auch für einen Stapel von Codes, dessen Antwort (jeder Code mit seinem Design) über 4 MB läge; es wird nichts erstellt. | Sende einen kleineren Body. Bei Codes ist meist ein großes Inline-Logo die Ursache; bei einem Stapel sende `Prefer: return=minimal` oder weniger Codes. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Ein Schreibzugriff ohne `Content-Type: application/json`. | Sende einen JSON-Body mit `Content-Type: application/json`. |
| 422 | `UNSAFE_DESTINATION` | Google Web Risk markiert die Ziel-URL (Malware, Phishing oder unerwünschte Software). Bei einem Array listet `data.details` jede markierte Zeile per `index` auf, und es wird nichts erstellt. | Verwende ein anderes Ziel. Wenn die Markierung falsch ist, bitte Google, die Website zu prüfen. |
| 429 | `RATE_LIMITED` | Zu viele Anfragen: ein Limit pro Minute (nur `Retry-After` ist gesetzt) oder das Tageskontingent des Workspace (`Retry-After` plus `X-RateLimit-*`). | Warte `Retry-After` Sekunden. Warte beim Tageskontingent bis 00:00 UTC oder wechsle den Tarif. |
| 500 | `INTERNAL_ERROR` | Auf Seiten von QRdx ist etwas fehlgeschlagen. Der Fehler wurde protokolliert. | Versuche es gleich noch einmal. Wenn es weiter auftritt, melde es mit der Uhrzeit der Anfrage. |
| 503 | `SLUG_UNAVAILABLE` | Es konnte nicht rechtzeitig ein freier Short-Link-Slug reserviert werden. | Sende dieselbe Anfrage noch einmal. |
| 503 | `UNAVAILABLE` | Eigene Domains sind in diesem Deployment nicht eingerichtet (eine selbst gehostete Instanz ohne sie). | Lass `domainId` weg oder konfiguriere eigene Domains auf deiner Instanz. |

## Wiederholen [#retrying]

- **`429`:** Warte die Anzahl an Sekunden aus `Retry-After` und sende dann dieselbe Anfrage. Wenn das Tageskontingent aufgebraucht ist, zeigen die `X-RateLimit-*`-Header, wie viele Anfragen der Tarif erlaubt und wann der Zähler zurückgesetzt wird (00:00 UTC). Siehe [Rate Limits](/docs/developers/rest-api#rate-limits).
- **`500` und `503`:** Wiederhole mit exponentiellem Backoff, beginnend bei etwa einer Sekunde.
- **Andere `4xx`:** Dieselbe Anfrage schlägt genauso fehl. Behebe zuerst den Fehler.

Das Erstellen von Codes ist nicht idempotent: Wenn ein `POST /v1/codes` in ein Timeout läuft, liste deine Codes auf, bevor du erneut sendest, sonst erstellst du den Code womöglich doppelt. Conversions sind idempotent: Sende deine eigene `id`, und eine Wiederholung gibt `200` mit `duplicate: true` zurück.

## `/v1/me` und `/v1/themes` [#v1me-and-v1themes]

Diese beiden Endpunkte senden denselben Body plus die OAuth-Felder, die sie schon immer gesendet haben, `error` und `error_description` (derselbe Text wie `message`), damit ältere Clients weiter funktionieren:

| `error` | `code` |
| --- | --- |
| `invalid_token` | UNAUTHORIZED oder INVALID_TOKEN |
| `insufficient_scope` | INSUFFICIENT_SCOPE |
| `rate_limited` | RATE_LIMITED (Tageskontingent) |
| `not_found` | NOT_FOUND (Themes) |

## OAuth-Endpunkte [#oauth-endpoints]

Die OAuth-Endpunkte unter `https://qrdx.dev/api/oauth` (authorize, token, revoke, userinfo) folgen stattdessen dem OAuth-2.0-Standard: `{ "error", "error_description" }`, wobei `error` einer von `invalid_request`, `invalid_client`, `invalid_grant`, `unsupported_grant_type`, `invalid_token` oder `access_denied` ist. Wenn du bei einem Refresh `invalid_grant` erhältst, wurde das Refresh-Token bereits verwendet (jeder Refresh gibt ein neues zurück), ist nach 30 Tagen abgelaufen oder der Nutzer hat deine App widerrufen: Schicke den Nutzer erneut durch die Autorisierung. Siehe [REST API und OAuth](/docs/developers/rest-api#get-an-access-token).

## Unbekannte Endpunkte [#unknown-endpoints]

Ein Pfad unter `/v1`, der nicht existiert, gibt `404 NOT_FOUND` als JSON zurück, nie eine HTML-Seite. Die [API-Referenz](/docs/developers/api) listet alle Endpunkte auf.
