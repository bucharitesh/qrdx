QRdx steht unter der AGPL-3.0-Lizenz, und du kannst die Web-App (QR-Editor, Konten, Zwei-Faktor-Authentifizierung und Passkeys, dynamische Codes und gehostete Seiten, Teams, gespeicherte Themes, Community-Galerie und diese Docs) auf deinem eigenen Server betreiben. Ausgenommen sind Single Sign-on für Workspaces und das Audit-Log des Workspace: Sie liegen in den kommerziell lizenzierten `ee/`-Ordnern und bleiben deaktiviert, solange du keinen Lizenzschlüssel (`QRDX_EE_LICENSE`) setzt. Für den Einsatz in der Produktion brauchst du eine schriftliche Vereinbarung mit QRdx; siehe [LICENSING.md](https://github.com/bucharitesh/qrdx/blob/main/LICENSING.md). Für die [`qrdx`-React-Bibliothek](/docs/getting-started) und die CLI brauchst du das alles nicht. Sie laufen überall ohne Backend.

<Callout type="warn">
  Das Docker-Setup ist neu. Wenn etwas nicht funktioniert, [öffne bitte ein Issue](https://github.com/bucharitesh/qrdx/issues).
</Callout>

## Voraussetzungen [#requirements]

- Docker mit Compose v2 und BuildKit (Docker Desktop und die aktuelle Docker Engine enthalten beides) oder Node.js 22 (22.22.3 oder neuer) und [Bun](https://bun.com/docs/installation) 1.4 für die manuelle Einrichtung
- Mindestens 8 GB Arbeitsspeicher für Docker, während das Image gebaut wird
- Eine Möglichkeit zur Anmeldung, damit Konten angelegt werden können: eine GitHub- oder Google-OAuth-App oder [Resend](https://resend.com) für E-Mail-Anmeldecodes. Codes werden nur per E-Mail verschickt, wenn `NEXT_PUBLIC_APP_URL` nicht `localhost` ist. `bun run dev` gibt sie stattdessen im Terminal aus, das Docker-Image tut das aber nicht. Für einen lokalen Docker-Test brauchst du daher die Anmeldung über GitHub oder Google.
- Postgres: der in `docker-compose.yml` enthaltene Container oder eine [Neon](https://neon.tech)-Datenbank

### So funktioniert die Datenbankverbindung [#how-the-database-connection-works]

Die App spricht über den Serverless-HTTP-Treiber von Neon mit Postgres.

- **Neon:** funktioniert direkt. Setze `DATABASE_URL` auf deinen Neon-Verbindungsstring.
- **Normales Postgres:** braucht einen Neon-kompatiblen HTTP-Proxy davor. `docker-compose.yml` startet einen ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) und setzt `DATABASE_HTTP_ENDPOINT`, damit die App ihre Abfragen dorthin sendet.

Das Schema stammt aus `packages/database/schema.ts` und wird mit `drizzle-kit push` angewendet.

## Schnellstart mit Docker Compose [#quick-start-with-docker-compose]

### 1. Repository klonen [#1-clone-the-repository]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
```

### 2. Umgebung konfigurieren [#2-configure-the-environment]

```bash
cp apps/docs/.env.example .env
```

Bearbeite `.env`:

- `BETTER_AUTH_SECRET`: erzeuge einen Wert mit `openssl rand -base64 32`
- `NEXT_PUBLIC_APP_URL`: die öffentliche URL deiner Instanz, zum Beispiel `https://qr.example.com`. Für einen lokalen Test lässt du `http://localhost:3000` stehen.
- `BETTER_AUTH_URL`: entkommentiere die Zeile und verwende denselben Wert
- `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`: aus einer [GitHub-OAuth-App](https://github.com/settings/developers) mit der Callback-URL `<your url>/api/auth/callback/github`
- oder `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`: aus einem [Google-OAuth-Client](https://console.cloud.google.com/apis/credentials) mit der Redirect-URI `<your url>/api/auth/callback/google`

`DATABASE_URL` musst du nicht setzen. Compose verbindet die App mit dem eigenen Postgres-Container. Um das Datenbankpasswort zu ändern, setze `POSTGRES_PASSWORD` vor dem ersten Start.

### 3. Stack starten [#3-start-the-stack]

```bash
docker compose up -d --build
```

Dadurch wird das Image gebaut, Postgres und der Proxy werden gestartet, der einmalige Service `migrate` (`drizzle-kit push`) läuft durch, und danach startet die App auf Port 3000. Der erste Build dauert einige Minuten.

```bash
docker compose ps                    # migrate should show "exited (0)"
docker compose logs -f migrate app   # follow the schema sync and the app
```

### 4. Ersten Nutzer anlegen [#4-create-your-first-user]

Öffne `NEXT_PUBLIC_APP_URL` im Browser und melde dich mit GitHub, Google oder einem E-Mail-Code an. Dein Konto wird bei der ersten Anmeldung erstellt.

### 5. Ersten Admin anlegen [#5-create-your-first-admin]

Trage die E-Mail-Adresse des soeben erstellten Kontos in `.env` ein:

```bash
ADMIN_EMAILS=you@example.com
```

Erstelle den App-Container neu, damit er die Änderung übernimmt, melde dich dann an und öffne `/admin`:

```bash
docker compose up -d app
```

`ADMIN_USER_IDS` funktioniert genauso, nur mit Nutzer-IDs.

## Neon oder eine andere verwaltete Datenbank verwenden [#using-neon-or-another-managed-database]

Du kannst das mitgelieferte Postgres überspringen und nur das App-Image starten:

```bash
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Setze `DATABASE_URL` in `.env` auf deinen Neon-Verbindungsstring und lass `DATABASE_HTTP_ENDPOINT` ungesetzt. Wende das Schema einmal an (und nach jedem Update erneut), und zwar mit dem Migrator-Image:

```bash
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Manuelle Einrichtung (Node.js) [#manual-setup-nodejs]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
bun install

cp apps/docs/.env.example apps/docs/.env.local          # then edit it

bun run db:push                                          # apply the schema
bun run --filter docs dev                                # http://localhost:3000
```

Für die Produktion baust du die App und startest sie:

```bash
bun x turbo build --filter=docs
bun run --filter docs start
```

`bun run db:push` verbindet sich mit dem Neon-Treiber und braucht daher eine Neon-Datenbank. Wenn du stattdessen das Docker-Postgres für die lokale Entwicklung nutzen willst, starte es mit `docker compose up -d db db-proxy`, wende das Schema mit `docker compose run --rm migrate` an und setze Folgendes in `apps/docs/.env.local`:

```bash
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

## Reverse-Proxy und HTTPS [#reverse-proxy-and-https]

Stelle die App hinter einen Reverse-Proxy wie Caddy, nginx oder Traefik, der TLS terminiert, und gib Port 3000 nicht direkt ins Internet frei. Rate Limiting, die Sicherheits-E-Mails und das [Audit-Log](/docs/help/teams/audit-log) lesen die Client-IP aus `X-Real-IP` und danach aus der ersten Adresse in `X-Forwarded-For`. Der Proxy muss diese Header also setzen, und die App darf nur über ihn erreichbar sein. Lass den Proxy `X-Real-IP` auf die Adresse setzen, von der er die Verbindung erhalten hat (in nginx: `proxy_set_header X-Real-IP $remote_addr;`). Ein Proxy, der `X-Forwarded-For` nur ergänzt, erlaubt es einem Client, eine beliebige Adresse an die erste Stelle zu setzen.

Sobald HTTPS eingerichtet ist, ändere `NEXT_PUBLIC_APP_URL` und `BETTER_AUTH_URL` auf die `https://`-URL, aktualisiere die OAuth-Callback-URLs und baue neu.

### Content-Security-Policy [#content-security-policy]

Produktions-Builds senden auf den eigenen Seiten von QRdx eine Content-Security-Policy: Angemeldete Seiten erhalten pro Anfrage eine frische Script-Nonce, vorgerenderte Seiten eine Allowlist von Script-Hosts. Gehostete Seiten (`/p`) erhalten eine lockere Policy, weil sie die Pixel der Besitzer ausführen und Medien von überall einbetten. Wenn dein Reverse-Proxy ebenfalls `Content-Security-Policy` setzt, erzwingen Browser beide, lass sie dort also weg. Setze `CSP_REPORT_ONLY=1` (beim Build und zur Laufzeit), um die Policy nur als Report-Only zu senden, während du ein neues Setup prüfst; Verstöße werden von `/api/csp-report` geloggt. Füge `CSP_HTTPS=1` hinzu, wenn du außerhalb von Vercel über HTTPS auslieferst, damit Browser jede `http://`-Ressource hochstufen.

## Aktualisieren [#updating]

Sichere zuerst die Datenbank:

```bash
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Dann ziehe die Änderungen und baue neu. Der `migrate`-Service gleicht das Schema erneut ab, bevor die App startet.

```bash
git pull
docker compose up -d --build
```

Führe bei der manuellen Einrichtung `git pull`, `bun install` und `bun run db:push` aus und baue dann neu.

Wenn eine Schemaänderung Daten löschen würde, fragt `drizzle-kit push` nach einer Bestätigung. Führe in diesem Fall `docker compose run --rm migrate` in einem Terminal aus, um die Änderungen zu prüfen und zu bestätigen.

## Fehlerbehebung [#troubleshooting]

- **„Invalid environment variables“ beim Start:** Das Log nennt jede fehlende oder ungültige Variable. Optionale Variablen müssen auskommentiert sein und dürfen nicht auf einen leeren Wert gesetzt werden.
- **„BETTER_AUTH_SECRET is missing“ oder „You are using the default secret“:** Setze `BETTER_AUTH_SECRET` und erstelle den Container neu.
- **OAuth-Fehler `redirect_uri` mismatch:** Die Callback-URL in deiner OAuth-App muss genau `<NEXT_PUBLIC_APP_URL>/api/auth/callback/<github|google>` lauten. Setze `BETTER_AUTH_URL` auf dieselbe Basis-URL.
- **Die App erreicht die Datenbank nicht (`fetch failed`):** Bei reinem Postgres muss `DATABASE_HTTP_ENDPOINT` auf den laufenden Proxy zeigen. Prüfe `docker compose ps db-proxy`.
- **`migrate` wird nie fertig:** `drizzle-kit push` wartet auf eine Bestätigung. Siehe [Aktualisieren](#updating).
- **Ein geänderter `NEXT_PUBLIC_*`-Wert hat keine Wirkung:** Baue das Image neu.
- **Port 4444 wird bereits verwendet:** Ändere die Port-Zuordnung von `db-proxy` in `docker-compose.yml`. Nur die lokale Entwicklung auf dem Host nutzt ihn.
- **„the --mount option requires BuildKit“:** Dein Docker hat kein BuildKit. Installiere das `buildx`-Plugin oder aktualisiere Docker.
- **Der Build bricht mit `Killed` oder Exit-Code 137 ab:** Docker hat keinen Arbeitsspeicher mehr. Gib Docker mindestens 8 GB (Docker Desktop: Settings → Resources) und führe `docker compose up -d --build` erneut aus.
- **„sign-in code email is off for this deployment“:** E-Mail-Codes werden nicht versendet, solange `NEXT_PUBLIC_APP_URL` auf `localhost` steht. Nutze für einen lokalen Test die Anmeldung mit GitHub oder Google.
