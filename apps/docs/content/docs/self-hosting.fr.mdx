QRdx est sous licence AGPL-3.0, et vous pouvez exécuter l'application web (éditeur de QR code, comptes, vérification en deux étapes et passkeys, codes dynamiques et pages hébergées, équipes, thèmes enregistrés, galerie communautaire et cette documentation) sur votre propre serveur. L'authentification unique (SSO) de l'espace de travail et le journal d'audit de l'espace de travail font exception : ils se trouvent dans les dossiers `ee/`, soumis à une licence commerciale, et restent désactivés tant que vous ne définissez pas de clé de licence (`QRDX_EE_LICENSE`). Leur utilisation en production nécessite un accord écrit avec QRdx ; consultez [LICENSING.md](https://github.com/bucharitesh/qrdx/blob/main/LICENSING.md). Vous n'avez besoin de rien de tout cela pour utiliser la [bibliothèque React `qrdx`](/docs/getting-started) ou la CLI. Elles fonctionnent partout, sans backend.

<Callout type="warn">
  La configuration Docker est récente. Si quelque chose ne fonctionne pas, [ouvrez une issue](https://github.com/bucharitesh/qrdx/issues).
</Callout>

## Prérequis [#requirements]

- Docker avec Compose v2 et BuildKit (Docker Desktop et les versions actuelles de Docker Engine incluent les deux), ou Node.js 22 (22.22.3 ou version ultérieure) et [Bun](https://bun.com/docs/installation) 1.4 pour l'installation manuelle
- Au moins 8 Go de mémoire pour Docker pendant la construction de l'image
- Un moyen de se connecter, afin que des comptes puissent être créés : une application OAuth GitHub ou Google, ou [Resend](https://resend.com) pour les codes de connexion par e-mail. Les codes ne sont envoyés par e-mail que lorsque `NEXT_PUBLIC_APP_URL` n'est pas `localhost`. `bun run dev` les affiche dans le terminal à la place, mais l'image Docker ne le fait pas : un test local avec Docker nécessite donc une connexion GitHub ou Google.
- Postgres : le conteneur fourni dans `docker-compose.yml`, ou une base de données [Neon](https://neon.tech)

### Fonctionnement de la connexion à la base de données [#how-the-database-connection-works]

L'application communique avec Postgres via le pilote HTTP serverless de Neon.

- **Neon :** fonctionne directement. Définissez `DATABASE_URL` avec votre chaîne de connexion Neon.
- **Postgres classique :** nécessite un proxy HTTP compatible Neon placé devant. `docker-compose.yml` en exécute un ([local-neon-http-proxy](https://github.com/TimoWilhelm/local-neon-http-proxy)) et définit `DATABASE_HTTP_ENDPOINT` pour que l'application y envoie ses requêtes.

Le schéma provient de `packages/database/schema.ts` et est appliqué avec `drizzle-kit push`.

## Démarrage rapide avec Docker Compose [#quick-start-with-docker-compose]

### 1. Cloner le dépôt [#1-clone-the-repository]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
```

### 2. Configurer l'environnement [#2-configure-the-environment]

```bash
cp apps/docs/.env.example .env
```

Modifiez `.env` :

- `BETTER_AUTH_SECRET` : générez-en un avec `openssl rand -base64 32`
- `NEXT_PUBLIC_APP_URL` : l'URL publique de votre instance, par exemple `https://qr.example.com`. Conservez `http://localhost:3000` pour un test local.
- `BETTER_AUTH_URL` : décommentez-la et utilisez la même valeur
- `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` : issus d'une [application OAuth GitHub](https://github.com/settings/developers) avec l'URL de rappel `<your url>/api/auth/callback/github`
- ou `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` : issus d'un [client OAuth Google](https://console.cloud.google.com/apis/credentials) avec l'URI de redirection `<your url>/api/auth/callback/google`

Vous n'avez pas besoin de définir `DATABASE_URL`. Compose relie l'application à son propre conteneur Postgres. Pour changer le mot de passe de la base de données, définissez `POSTGRES_PASSWORD` avant le premier démarrage.

### 3. Démarrer la stack [#3-start-the-stack]

```bash
docker compose up -d --build
```

Cette commande construit l'image, démarre Postgres et le proxy, exécute le service ponctuel `migrate` (`drizzle-kit push`), puis démarre l'application sur le port 3000. La première construction prend plusieurs minutes.

```bash
docker compose ps                    # migrate should show "exited (0)"
docker compose logs -f migrate app   # follow the schema sync and the app
```

### 4. Créer votre premier utilisateur [#4-create-your-first-user]

Ouvrez `NEXT_PUBLIC_APP_URL` dans un navigateur et connectez-vous avec GitHub, Google ou un code reçu par e-mail. Votre compte est créé lors de la première connexion.

### 5. Créer votre premier administrateur [#5-create-your-first-admin]

Ajoutez à `.env` l'adresse e-mail du compte que vous venez de créer :

```bash
ADMIN_EMAILS=you@example.com
```

Recréez le conteneur de l'application pour qu'il prenne en compte la modification, puis connectez-vous et ouvrez `/admin` :

```bash
docker compose up -d app
```

`ADMIN_USER_IDS` fonctionne de la même manière avec des identifiants d'utilisateur.

## Utiliser Neon ou une autre base de données managée [#using-neon-or-another-managed-database]

Vous pouvez ignorer le Postgres fourni et n'exécuter que l'image de l'application :

```bash
docker build -t qrdx --build-arg NEXT_PUBLIC_APP_URL=https://qr.example.com .
docker run -d --env-file .env -p 3000:3000 qrdx
```

Définissez `DATABASE_URL` dans `.env` avec votre chaîne de connexion Neon et laissez `DATABASE_HTTP_ENDPOINT` non défini. Appliquez le schéma une fois (puis après chaque mise à jour) avec l'image de migration :

```bash
docker build --target migrator -t qrdx-migrate .
docker run --rm -e DATABASE_URL="<your connection string>" qrdx-migrate
```

## Installation manuelle (Node.js) [#manual-setup-nodejs]

```bash
git clone https://github.com/bucharitesh/qrdx.git
cd qrdx
bun install

cp apps/docs/.env.example apps/docs/.env.local          # then edit it

bun run db:push                                          # apply the schema
bun run --filter docs dev                                # http://localhost:3000
```

Pour la production, construisez puis démarrez l'application :

```bash
bun x turbo build --filter=docs
bun run --filter docs start
```

`bun run db:push` se connecte avec le pilote de Neon, il nécessite donc une base de données Neon. Pour utiliser plutôt le Postgres de Docker en développement local, démarrez-le avec `docker compose up -d db db-proxy`, appliquez le schéma avec `docker compose run --rm migrate`, puis définissez ces valeurs dans `apps/docs/.env.local` :

```bash
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/qrdx
DATABASE_HTTP_ENDPOINT=http://localhost:4444/sql
```

## Reverse proxy et HTTPS [#reverse-proxy-and-https]

Placez l'application derrière un reverse proxy comme Caddy, nginx ou Traefik qui termine le TLS, et n'exposez pas directement le port 3000 sur Internet. La limitation de débit, les e-mails de sécurité et le [journal d'audit](/docs/help/teams/audit-log) lisent l'IP du client dans `X-Real-IP`, puis dans la première adresse de `X-Forwarded-For` ; le proxy doit donc définir ces en-têtes et l'application ne doit être accessible qu'à travers lui. Faites en sorte que le proxy définisse `X-Real-IP` sur l'adresse depuis laquelle il a reçu la connexion (dans nginx, `proxy_set_header X-Real-IP $remote_addr;`). Un proxy qui se contente d'ajouter une adresse à `X-Forwarded-For` permet à un client de placer n'importe quelle adresse en premier.

Une fois HTTPS en place, remplacez `NEXT_PUBLIC_APP_URL` et `BETTER_AUTH_URL` par l'URL en `https://`, mettez à jour les URL de rappel OAuth, puis reconstruisez.

### Content-Security-Policy [#content-security-policy]

Les builds de production envoient une Content-Security-Policy sur les pages propres à QRdx : les pages pour les utilisateurs connectés reçoivent un nonce de script neuf à chaque requête, les pages prérendues une liste d'hôtes de scripts autorisés. Les pages hébergées (`/p`) reçoivent une politique permissive, car elles exécutent les pixels de leur propriétaire et intègrent des médias de n'importe quelle origine. Si votre reverse proxy définit aussi `Content-Security-Policy`, les navigateurs appliquent les deux : ne la définissez donc pas à cet endroit. Définissez `CSP_REPORT_ONLY=1` (au moment du build et à l'exécution) pour envoyer la politique en mode rapport seul pendant que vous vérifiez une nouvelle configuration ; les violations sont consignées par `/api/csp-report`. Ajoutez `CSP_HTTPS=1` lorsque vous servez en HTTPS hors de Vercel, afin que les navigateurs mettent à niveau toute ressource en `http://`.

## Mise à jour [#updating]

Sauvegardez d'abord la base de données :

```bash
docker compose exec db pg_dump -U postgres qrdx > qrdx-backup.sql
```

Récupérez ensuite les changements et reconstruisez. Le service `migrate` synchronise de nouveau le schéma avant le démarrage de l'application.

```bash
git pull
docker compose up -d --build
```

Pour l'installation manuelle, exécutez `git pull`, `bun install` et `bun run db:push`, puis reconstruisez.

Si une modification du schéma supprimait des données, `drizzle-kit push` demande une confirmation. Dans ce cas, exécutez `docker compose run --rm migrate` dans un terminal pour examiner et confirmer les modifications.
## Dépannage [#troubleshooting]

- **« Invalid environment variables » au démarrage :** le journal nomme chaque variable manquante ou invalide. Les variables facultatives doivent être commentées, et non définies avec une valeur vide.
- **« BETTER_AUTH_SECRET is missing » ou « You are using the default secret » :** définissez `BETTER_AUTH_SECRET` et recréez le conteneur.
- **Erreur de `redirect_uri` OAuth :** l'URL de rappel dans votre application OAuth doit être exactement `<NEXT_PUBLIC_APP_URL>/api/auth/callback/<github|google>`. Définissez `BETTER_AUTH_URL` sur la même URL de base.
- **L'application n'atteint pas la base de données (`fetch failed`) :** avec Postgres classique, `DATABASE_HTTP_ENDPOINT` doit pointer vers le proxy en cours d'exécution. Vérifiez avec `docker compose ps db-proxy`.
- **`migrate` ne se termine jamais :** `drizzle-kit push` attend une confirmation. Consultez [Mise à jour](#updating).
- **Une valeur `NEXT_PUBLIC_*` modifiée n'a aucun effet :** reconstruisez l'image.
- **Le port 4444 est déjà utilisé :** modifiez le mappage de port de `db-proxy` dans `docker-compose.yml`. Seul le développement local sur l'hôte l'utilise.
- **« the --mount option requires BuildKit » :** votre Docker n'a pas BuildKit. Installez le plugin `buildx` ou mettez Docker à jour.
- **La compilation s'arrête avec `Killed` ou le code de sortie 137 :** Docker a manqué de mémoire. Allouez-lui au moins 8 Go (Docker Desktop : Settings → Resources), puis relancez `docker compose up -d --build`.
- **« sign-in code email is off for this deployment » :** les codes par e-mail ne sont pas envoyés tant que `NEXT_PUBLIC_APP_URL` vaut `localhost`. Utilisez la connexion GitHub ou Google pour un test en local.
